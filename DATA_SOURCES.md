# Data Sources & Attribution

God's Eye View's **code** is [MIT](LICENSE)-licensed. **The MIT grant covers the source code only — it does NOT extend to third-party data or visual assets.** Every third-party source keeps its own license and terms. This file documents the live and bundled data sources; bundled 3D-model provenance is recorded in [`public/models/README.md`](public/models/README.md).

How to read this:

- **The non-permissive datasets are carved out, not omitted.** Some bundled data (e.g. TeleGeography, CC BY-NC-SA) isn't MIT-compatible. Rather than hide it, we **bundle it with a clear license carve-out** so the app works out of the box — but it stays under the provider's terms.
- **If your use doesn't fit a dataset's license, remove that dataset.** Most importantly: TeleGeography is **NonCommercial** — commercial users must delete it (or license it from TeleGeography). It's one self-contained folder.
- **Attribution is shown in-app** and listed here. Keep it intact. The required Google/Cesium credit renders on the on-globe credit line (bottom-left, `#cesium-credits`), and every per-layer credit below is registered into the expandable **"Data attribution"** lightbox on that line (`src/data/dataCredits.js` → `viewer.creditDisplay.addStaticCredit`). Both stay visible in clean-view and recording modes.
- **Bundled model attribution lives beside the model files.** [`public/models/README.md`](public/models/README.md) records each shipped model's creator, source, license, and modification status.
- **README media provenance lives beside the media.** [`docs/media/README.md`](docs/media/README.md) records the creator and likeness permissions for the 17 capture GIFs, plus the public source, publication permission, and reuse boundary for the two README PNGs. Third-party content visible within this media remains subject to its provider or owner's terms.

IDFM publishes **no GTFS-Realtime vehicle positions at all** (see `src/data/transitCoverage.js`), so this layer draws the network offer and never a simulated vehicle |
| **Re:Earth Terrain** (Mapterhorn) | Terrain (keyless globe stacks — OSM etc. — + `/api/terrain/heights` ellipsoidal-height lookups) | Terrain mesh: CC BY 4.0; geoid: EGM2008 (NGA, public domain) | "Terrain (keyless globe stacks): Re:Earth Terrain / Mapterhorn (CC BY 4.0) / EGM2008 (NGA)" |

### Notes on the live sources

- **Bison Futé — Événementiel-DIR.** The feed covers the **réseau routier national non concédé** and nothing else. The conceded motorways — the ASF / APRR / Sanef network — are not in it: Bison Futé serves those through the credentialed *Action b* and *Action c* licences of the [directive STI](https://www.bison-fute.gouv.fr/directive-sti,id_sous_rubrique10402.html), which this app has not requested. The layer states that coverage on its row and in this file rather than letting an empty motorway read as an empty motorway. (The same publisher's QTV-DIR speed/flow snapshot is read separately by the Road Status FR layer, above.)

  Two properties of the source are worth writing down, because each is a way to be wrong about it:

  - **A `Linear` event publishes only its two endpoints.** The road's shape between them is not in the feed; reconstructing it needs the RRN référentiel Bison Futé distributes separately. Segments are therefore drawn as the straight chord between the published ends. Measured on the 2026-08-31 snapshot: 409 segments, median chord 1.77 km, p90 6.5 km, 21 longer than 10 km, and the card says so past 10 km.
  - **A situation is not an event.** DATEX II nests up to twelve records inside one situation — the accident, the lanes it blocked, the exits it closed — so one drawn marker per situation is the honest unit, with the rest counted on its card. Records the feed marks `probable` or `riskOf` are forecasts and are labelled as unconfirmed.

  The proxy fetches the document with `If-None-Match`: measured 2026-08-31, the origin serves ETag, Last-Modified and gzip (3,365,501 → 165,296 bytes) and answers a conditional GET with a 304, which is what makes polling a 3.3 MB document every five minutes affordable.

- **Google Maps Platform.** You supply your own API key and are bound by [Google's ToS](https://cloud.google.com/maps-platform/terms). Google Maps Content (tiles, geocodes, places) **may not be cached, stored, rehosted, or committed** — this app only ever uses it live, which is the compliant pattern. The "Google" attribution is displayed on the globe and must stay visible. Restrict your key (see [SECURITY.md](SECURITY.md)).
- **OpenSky Network.** Its license is **non-commercial**, and operational use of the REST API in a live product can require a prior written agreement with OpenSky — even for non-profit/government use. If you deploy this commercially, contact OpenSky for your own terms. The flights layer is a toggle and runs anonymously by default.
- **adsb.lol flight fallback.** When OpenSky is unavailable and no last-good OpenSky response exists, the server requests a cached, capped 250 nm adsb.lol point snapshot around the current camera subpoint. This is regional observed context, not worldwide completeness; provenance is exposed in the Flights stats/context row. Military ICAOs remain reconciled through the existing dedicated military registry rather than duplicated.
- **Launch Library 2.** `/api/launches` makes a server-side rolling-30-day query against the supported v2.3 detailed launch endpoint, caches successful responses for 15 minutes in memory and on disk, and serves the last successful response during a throttle or transient outage. Anonymous access is limited to 15 calls/hour; deployments can provide `LL2_API_TOKEN` for authenticated access. The Space Devs' published terms permit using and sharing the API data in any form, ask users not to forward it without adding value, disclaim complete accuracy, and encourage—but do not require—attribution. This app keeps a courtesy credit. Payload and stage/recovery records are shown only when supplied. Failed launches expose their source status and never receive fallback orbit geometry or a live/estimated marker. LL2 supplies launch context and event timing, not continuous ascent telemetry or live orbital state.
- **TfL JamCams.** The camera list comes from the keyless `api.tfl.gov.uk` endpoint (an optional `TFL_APP_KEY` raises its rate limit); frames come from TfL's public S3 bucket. The "Powered by TfL Open Data" attribution is required by TfL's terms and is registered in the Data attribution popover.
- **OSM mapped cameras.** Opt-in (`CCTV_OSM_CAMERAS_ENABLED=1`) and off by default. OpenStreetMap records where a camera **is**, never what it sees, so this source contributes `man_made=surveillance` camera **positions** with no upstream feed URL: each frame request falls through the CCTV proxy's existing chain to a **billable Google Street View still** (health `degraded`, `SRC STREETVIEW`) or the synthetic `NO UPSTREAM CONFIGURED` placeholder — the reason it is not a default. Only `surveillance=public|outdoor|traffic` cameras are kept (indoor, untagged-scope, ALPR, and guard-post records are excluded rather than presented as public cameras); the mapped set is incomplete and reflects volunteer mapping, not a camera registry. Pose uses the mapped tags where they exist — bearing (`camera:direction`/`direction`), tilt from the horizon (`camera:angle`), mount height (`height`/`camera:mount`), and the rarely-mapped aperture (`camera:fov`, ~61 uses worldwide) — and **modeled priors** (`camera:type` cone width, mount-height tilt steps, a deterministic id-hash bearing) everywhere OSM is silent, so every camera stays `RAW PRIOR` in the CAL badge until a human calibrates it; a multi-value `camera:direction` renders its first facing at reduced confidence. Loading is **viewport-bounded**, never a country download: `/api/osm-cameras` answers one allow-listed tag query inside a box no wider than 2°, snapped outward onto a shared grid so neighbouring views share one cached answer, capped at 400 elements (a truncated box is reported as `saturated`), cached 5 min in memory and 7 days on disk under `.gev-cache/osm-cameras/` with serve-stale on failure. The client asks only on camera settle (500 ms debounce), holds at most 120 of these cameras at once, and evicts the ones you leave behind through the same grace planner the ambient cards use. The ODbL credit is registered dynamically — only once mapped positions actually appear on the globe.
- **Grand Lyon Criter cameras.** The camera list comes from the keyless `data.grandlyon.com` datapusher endpoint (no token, no quota); frames sit on the Métropole's own `download.data.grandlyon.com` host and are re-extracted from the live video by the Criter traffic-control system once a minute — the same stills Onlymoov publishes. Measured 2026-08-26 by hashing one camera's JPEG every 20 s for three minutes: three distinct frames, 62 s apart. That cadence is served to the client as `upstreamCadenceMs` so the active-camera poll matches the publisher instead of re-fetching the same picture five times out of six. Rows are dropped unless their frame URL is on that official origin and their `last_update` stamp has moved within the last 12 hours (the catalog carries no in-service flag, so a frozen stamp is the only decommissioned-camera signal). Licence Ouverte 2.0 requires attribution to the Métropole de Lyon; it is registered in the Data attribution popover. Set `CCTV_LYON_ENABLED=0` to drop the pack.
- **Power grid (OpenStreetMap).** Keyless, ODbL, viewport-loaded, and the reason it exists is that **RTE publishes no public geometry for its network** — the éCO2mix and gas layers come from ODRÉ, but the wires themselves are only mapped by volunteers. So this layer is **community mapping, not a grid register**: coverage is excellent in western Europe and uneven elsewhere, and a line that is not drawn is not a line that does not exist. **Voltage is the filter, because voltage is the evidence**: only features OSM has given a voltage of **50 kV or more** are drawn at all — nothing is demoted to a guess, and a feature with no `voltage` tag is simply absent. The four bands (≥ 300 / 180–299 / 100–179 / 50–99 kV) are deliberately generic rather than a list of French nominal voltages, so the palette reads correctly on the French (400/225/90/63), British (400/275/132) and German (380/220/110) grids alike — verified live against central London, 2026-08-27. **Routes are drawn on the ground.** A conductor hangs tens of metres up and OSM records that for a minority of pylons and for no line at all, so the layer draws the mapped GROUND ROUTE as a clamped ground polyline and says so on every card and every legend row; underground `power=cable` is dashed so it is never read as a pylon route. **A stroke is not a line** — OSM splits one named liaison across dozens of ways, so the layer reports the stroke count it drew *and* the distinct mapped route names behind them (measured 2026-08-27, Île-de-France: 1,386 strokes for 304 named routes). Loading is **viewport-bounded**, never a country download: `/api/power-grid` answers one allow-listed query inside a box no wider than 0.8°, snapped outward onto a shared 0.05° grid so neighbouring views share one cached answer, with a **separate element cap per class** (2,600 strokes; 300/120/60 substation ways/nodes/relations; 2,000 pylons) — one shared cap starves whatever Overpass emits last, which in a Paris viewport meant 899 pylons erasing every line and substation in the box. Pylons are requested only below 0.25° of view. Truncation is reported **per class** and surfaced in the layer readout, because a truncated stroke set has gaps in it. Cached 10 min in memory and 7 days on disk under `.gev-cache/power-grid/`, with serve-stale on failure; a failed load retries on a 20 s → 240 s backoff, which public Overpass mirrors make routine (a cold request on 2026-08-27 drew 504, 502, 504 and a timeout from four mirrors, and the next one answered in 2.2 s). Measured the same day: a 0.1° × 0.14° box is 174 KB / 2.2 s cold and 4 ms warm; a 0.5° box 738 KB / 7.2 s; the widest box the client can ask for, 0.8° over Île-de-France, is 1.15 MB / 14.8 s and is the one case that saturates the stroke cap. The ODbL credit is registered statically, like the other OSM sources. **And the coverage claim is measured, not asserted.** `npm run qa:power-grid-coverage` compares OSM against RTE's OWN register — the one RTE published until 2023 and then withdrew — and on 2026-08-28 found that of 4,067 in-service *postes de transformation* at ≥ 50 kV, **98.5 % have an OSM substation carrying ≥ 50 kV within 1 km**, at a median positional offset of **13 m**, with **98.7 %** voltage agreement and **not one of the 192 sites at ≥ 300 kV missing**. Only 11 are genuinely absent from OSM (0.27 %); of the rest of the misses, 27 are mapped by OSM with no usable voltage, which our own ≥ 50 kV filter drops rather than guess. The reference data is downloaded into the gitignored `.gev-cache/grid-audit/` and is never republished by the app — see `scripts/grid-audit/README.md`, which also records the two traps that audit had to survive (RTE's export counts tap-offs on pylons as "sites", and one Overpass mirror serves a Switzerland-only extract that answers France with a confident zero).
- **Per-unit generation (RTE + ODRÉ + OpenStreetMap).** The one layer on this globe that needs an account, and the only one that draws its whole subject WITHOUT it. **RTE publishes no coordinate for any generating unit** — `actual_generations_per_unit` returns an EIC code, a name, a production type and a number of megawatts — so the fleet itself comes from ODRÉ's *Registre national des installations de production et de stockage d'électricité*, which publishes those same EIC codes with installed power, filière and commune (measured 2026-08-28: 171 units at or above the 100 MW publication floor, all 171 with a distinct EIC, 57 of them reactors for 63.0 GW). That register is baked into a shipped file by `npm run rte:units`, so a `git clone` with no key draws all 108 stations and 93.5 GW of installed capacity; the RTE credential only ever adds the number that is moving. **Positions are derived from four published anchors and every station says which one it got**: 69 sit on **EDF's own published coordinate for its own station**, 11 on an OpenStreetMap `power=plant` outline, 13 on the `ref:FR:RTE` switchyard the register names, and 15 at the centre of their commune from geo.api.gouv.fr — including four offshore wind farms whose rings are therefore on the beach, because OSM maps no `power=plant` for them and nothing else publishes their footprint. A candidate more than 30 km from the commune centre is refused rather than trusted, and two anchors are never averaged. **EDF outranks OpenStreetMap** because, measured 2026-08-28 across the 69 stations where both publish a position, they agree to within 300 m on every reactor and every thermal site and diverge by up to 9.5 km on hydro — where a powerhouse, an intake and a dam share a name across a valley and the operator is the only party who knows which is the station; taking EDF's moved 11 stations more than 500 m closer to the commune the register independently names and 6 more than 500 m further, and every `edf-published` row records `supersededOsmKm` so the choice is auditable per station rather than asserted. The two country-wide Overpass queries behind the OSM tiers are cached on disk, and a build that cannot reach OpenStreetMap **fails** rather than silently writing a registry with every non-EDF station demoted to its commune centre. **No reactor is drawn individually**: OpenStreetMap has zero `power=generator` + `generator:source=nuclear` elements over France, so Gravelines is one ring with six groups on its card rather than six invented discs. On screen, a **faint empty ring** is a station RTE published nothing for and a **crisp empty ring** is one measured at zero — an outage, which is the state a `value || 0` guard erases and the single most interesting thing a reactor does; a **magenta disc** is a machine CONSUMING the grid, which pumped storage and batteries genuinely do. Auth is OAuth2 client-credentials over HTTP Basic against `digital.iservices.rte-france.com/token/oauth/` (verified live 2026-08-28: an unauthenticated call answers `invalid_client`, and the resource answers `WWW-Authenticate: Bearer … "Unable to find token in the message"`), with the token cached and refreshed once on a 401. The window asked for is Paris-local yesterday 00:00 → tomorrow 00:00, which always contains the last published hour — a same-day window is empty at 00:30 — and a refused window falls back to the resource's own default, reported as `window.mode`. Cached 5 minutes in memory and on disk under `.gev-cache/rte-generation.json`. `/api/rte-generation` answers **200 with `auth: "missing"`** when there is no credential, because the layer's map does not depend on it. **Verified against the live resource 2026-08-28** through a free account: the 48-hour dated window is accepted (200, 980 KB, 1.2 s), 152 units are published at hourly resolution with a ~10 minute lag, and all of them share one latest hour. Three things that verification changed: the resource sends **no `installed_capacity`** (0 of 152), so the register's `puismaxinstallee` is the denominator behind every load figure; it sends **no nulls** (0 of 6 992 rows), so the future-padding guard is defensive rather than observed; and **negative readings are mostly shut-down units drawing house load, not pumps** — 24 units read negative and 14 were REACTORS, Chooz 1 at −58 MW, because a stopped 1 500 MW reactor still runs its coolant pumps and buys that power back. **The two publishers also cut the fleet at different granularities**, which is the join's real limit: the register carries one row per hydro PLANT and RTE publishes its turbine GROUPS under entirely different EIC codes, leaving 55 of 152 units — 36% of the fleet, 1 914 MW — unplaceable by code. Those reach their station through a name match on RTE's `<STATION> <n>` unit name, recorded per unit as `matchedBy: 'name'` and stated on the card, and an ambiguous name is refused rather than assigned. Four units stay unplaced and are reported as such.

- **Grand Lyon camera headings are estimated, not published.** The catalog carries no bearing: its `observation` field names a destination ("Direction : Porte de Gerland"), not a facing. Fourteen of the fifteen cameras therefore carry a **hand-derived** heading (`GRANDLYON_CURATED_HEADINGS` in `vite.config.js`), built from two independent halves — the azimuth of the carriageway under the camera, computed from OpenStreetMap way geometry, and the sign of that azimuth, taken from the geocoded destination or, where that was ambiguous, from landmarks and solar shadow direction in the published frame itself. These are careful estimates from public geometry and imagery, **not surveyed values and not published by the Métropole**; they are served as `poseSource: 'curated'` so the panel badge reads `CAL · CURATED` rather than implying a measurement, and the calibration gizmo still overrides them. The fifteenth camera keeps the low-confidence id-hash fallback, like a headingless Austin row or any TfL JamCam.
- **Provider "image unavailable" placeholders.** When a Criter camera is down the Métropole serves a fixed graphic of traffic cones in place of a frame — as a valid HTTP 200 JPEG, while the catalog row's `last_update` keeps advancing every minute. No status field, freshness check, or HTTP code catches it. The proxy therefore fingerprints that image by content hash (`isPlaceholderCctvFrame`) and treats it as a failed fetch, so it falls into the usual Street View / synthetic chain and the health line says the provider is serving a placeholder instead of reporting `SNAPSHOT · OK` over a picture of road cones. The check fails open: an unrecognised body is always served unchanged.
- **Grand Lyon incomplete frames.** One camera (`CWL5801`, Tunnel sous Fourvière — at 1920x1440 the largest frame in the pack) publishes a JPEG that ends before its scan data does: a valid HTTP 200, chunked so there is no Content-Length to fall short of, with the full frame size still declared in the header. A browser paints the rows it received and leaves the rest transparent, so the camera renders as a thin strip of sky. Measured 2026-08-26: 12 fetches 7 s apart, 0 complete, byte count stable within each publication minute — the published file is itself incomplete every cycle, so a retry cannot win it. `isTruncatedJpegFrame` looks for the JPEG end-of-image marker in the tail of the body and routes anything missing it into the same fallback chain, with the reason on the health line. Non-JPEG bodies are never judged, and the tail window is sized to clear trailing metadata without mistaking an EXIF thumbnail's own marker for the real one.
- **transport.data.gouv.fr (the PAN).** France's national access point for mobility data, operated under EU regulation 2017/1926 — a public, keyless **directory**, not a feed. `GET /api/datasets` returned 784 datasets on 2026-08-31, of which **150 resources declare the `vehicle_positions` feature** (781 and 151 on 2026-08-26 — the catalog moves). That set is what the Transit FR layer reads, one Protocol Buffers body per network, decoded server-side (`src/data/gtfsRealtime.js`, on the `pbf` dependency the traffic tiles already use — no `gtfs-realtime-bindings`). Licences are carried **per feed**, verbatim from the catalog, and shown on the vehicle card; every one of them is attribution-only.
- **PAN coverage is real but uneven, and the gap is a publication choice, not a format barrier.** Vehicle positions are densest in mid-size métropoles and régions — Bordeaux (TBM), Rouen/Normandie (Astuce), Le Havre (LiA), Nice (Lignes d'Azur), Montpellier (TaM), Rennes (STAR), Angers (Irigo), Lens-Liévin (TADAO), Occitanie (liO), Pays de la Loire (Aléop). The **largest** networks publish no live vehicle positions **at all**: Île-de-France, Lyon, Marseille, Strasbourg and Lille expose SIRI, and the SIRI they expose is next-departure and disruption data, not coordinates. Verified 2026-08-26 three ways: (1) **zero** of the 105 SIRI / SIRI Lite resources in the catalog declare the `vehicle_positions` feature; (2) the French SIRI profile makes only `EstimatedTimetable` mandatory and leaves `VehicleMonitoring` — the service that would carry positions — merely *recommended*; (3) Île-de-France Mobilités' own functional documentation lists exactly four entry points (`stop-monitoring`, `departures`, `estimated-timetable`, `general-message`) and describes the vehicle's position as an **input** to its arrival predictions, never as an output: *"Prédictions d'horaires de prochains passages prenant en compte la position réelle du véhicule"*. The GPS exists; what leaves the platform is a predicted minute at a stop. So a camera over central Paris correctly reports *"no PAN feed covers this view"* — and no SIRI decoder would change that, because there is nothing there to decode. Sampled 2026-08-26 at 19:33 local: all 151 GTFS-RT feeds answered, 4,105 vehicles were reporting, and 26 feeds returned an empty body (school and seasonal services outside their operating window).
- **Feed footprints are OBSERVED, never declared.** The catalog publishes coverage as a *name* (`{type: 'epci', nom: 'Bordeaux Métropole'}`) and never as geometry, so nothing in the source can answer "which feeds are on screen". `config/pan_gtfs_rt_feeds.json` (built by `scripts/build-pan-gtfs-rt-index.mjs`, committed so a cold start costs no probe sweep) therefore records the bounds of the vehicles each feed **actually reported** when probed. Read it as a floor, not a boundary: a network's real service area is at least as large as its box, an off-peak probe sees less of it, and a feed with nothing running gets no box at all. Junk fixes are fenced out before measuring — three Normandy networks on one platform each reported a vehicle at 27.14 N, 3.40 W (the Algerian Sahara) during that build, and one such fix turns a 40 km city footprint into a 2,500 km one that then matches every viewport in western Europe. The dev-server proxy keeps growing these bounds at runtime (grow-only, cached under `.gev-cache/pan-transit-bounds.json`) and gives boxless feeds a small rotating allowance so a dormant network can reveal itself — spent only within ~1.5° of somewhere a feed has actually been observed, so a camera over Tokyo never probes French buses.
- **What each vehicle IS, joined at build time.** GTFS-Realtime carries no `route_type`, so the vehicle's class lives in its network's static GTFS. `scripts/build-pan-route-types.mjs` reads **one member** out of each remote archive — `routes.txt`, 8.7 KB inside Bordeaux TBM's 26.7 MB / 250 MB-expanded feed — and commits `config/pan_route_types.json`: 147 feeds, 7,044 routes, 195 KB. Where the publisher honours HTTP `Range` (as `transport.data.gouv.fr` does) `scripts/lib/remoteZip.mjs` pulls it from a 50 MB archive in ~80 KB of transfer, walking the ZIP central directory backwards and inflating just that entry; where it does not — several publishers stream their archive chunked from origin, and three (Nice, Angers Irigo, TADAO) write ZIP64 extended-information fields — the whole body is read once and discarded. The whole national build costs ~136 MB instead of ~1.5 GB. `shapes.txt` (20 MB for Bordeaux alone) and `trips.txt` (7 MB, and re-minted with every GTFS version) are deliberately **not** committed. Measured 2026-08-31 the join types **92.7% of the national live fleet**: 86.9% from the vehicle's own `route_id`, the rest from networks where every published route is one class (TADAO publishes 333 routes and all 333 are buses, so an unmatched id there is still a bus). Three networks resolve nothing — Tours Fil Bleu and one of Le Havre's two feeds publish no usable `route_id`, Valenciennes Transvilles publishes ids that are in no `routes.txt` — and those keep the neutral glyph and read `Type unknown`, with the *network's* service class offered as what it is. Only then does a Bordeaux viewport separate its 67 trams and 3 Garonne shuttles from its 358 buses.
- **The shipped index is deduplicated and self-quarantining.** The catalog lists resources, not networks, and some networks publish one body twice: measured 2026-08-31, Kicéo's two resources returned the same 59 vehicles and Réseau Pybus's the same 5, each drawn twice. `src/data/panFeedHealth.js` finds candidates by a positional fingerprint (`localId@lat,lon`) and **confirms them on a second probe by roster only** — the fleet has moved in between, so demanding identical coordinates twice tests the upstream's refresh timing rather than whether two resources are one feed. A confirmed duplicate is sticky and only contrary evidence clears it. Separately, a run of failed probes quarantines a feed out of viewport selection without deleting it, and any single success revives it. Nothing is removed from the file; `/api/transit-fr/feeds` reports **shipped** and **queryable** counts side by side (150 and 148 on 2026-08-31).
- **Delay and disruption come from the SAME networks, joined to the vehicle already on screen.** GTFS-Realtime's other two messages are `TripUpdate` (what the operator expects at each remaining stop of a running trip) and `Alert` (what it has written about a line). Measured 2026-08-31, **all 150** vehicle-position feeds have a trip-update companion in their own dataset and **60** have an alert one — and **63 of the position feeds carry all three entity types in ONE resource**, so for those the delay costs no second request, only a second read of bytes already fetched. Which resource pairs with which position feed is not in the catalog and is **measured** rather than guessed: `scripts/build-pan-gtfs-rt-index.mjs` probes each candidate and keeps the one whose trips actually join that feed's own vehicles, committing the join rate with it. Adjacent resource ids are only the ranking hint — they pair Montpellier TaM's urban and suburban feeds correctly and get Rouen Astuce wrong, where three position feeds and four trip-update feeds interleave one operator per id. Mean measured join rate over the 79 networks with vehicles running at build time: **0.92**. At runtime the companion is fetched only when a feed actually has vehicles **inside the requested box** (TBM's trip updates are 1.2 MB against 37 KB of positions), cached 45 s for trip updates and 5 min for alerts, with a 6 s timeout — shorter than the position timeout, because a slow prediction server must never hold up the fleet behind it.
- **A deviation is only published by about a third of the fleet, and the rest say so.** Over the 30 largest live networks on 2026-08-31 (1,865 vehicles): **67%** of vehicles join a trip update on `trip_id` and a further 2% only on the vehicle id (TANGO and Tours Fil Bleu publish trip ids in their position feed that appear nowhere in their own trip updates); **38%** end up with a schedule deviation. The 29-point gap is not a join failure — **17 of those 30 networks publish `StopTimeEvent.time`, an absolute predicted time, and never `StopTimeEvent.delay`**, and converting one into the other requires the scheduled time from the static `stop_times.txt` (223 MB expanded for Bordeaux alone, re-minted with every GTFS version), which this project does not load. `TripUpdate.delay`, the trip-level field, was published by **nobody**. So a vehicle whose run was matched but whose operator published no deviation reads *"run tracked · no delay published"*, and one that matched nothing says nothing at all — a card that simply omitted the line would make "on time" and "never said" indistinguishable. Where a deviation exists it is read at the stop that describes where the vehicle IS (its own `current_stop_sequence`, published by 42% of the fleet; otherwise the first stop still in the future), and the card names the weaker readings.
- **A bus on layover is not a bus running early.** A vehicle parked at its terminus waiting for a departure 56 minutes away publishes a predicted arrival of "about now" against a scheduled arrival 56 minutes ahead, and the operator's own arithmetic gives −3,361 s. Measured over Bordeaux, Rouen, Normandy, Le Havre and Montpellier on 2026-08-31, **19 of the 22 vehicles more than five minutes "early" were stopped at stop sequence 1**. `src/data/transitSchedule.js` reclassifies those as *waiting to depart*, with the scheduled departure the vehicle is waiting for, and makes no punctuality claim about them. The rule is one-sided: a vehicle at its first stop running LATE has an overdue departure, which is lateness a rider feels. Alerts are attached by the most specific thing they inform — this run, then this line, then the network — and the **scope travels with the text**, because "your bus is diverted" and "this line is diverted somewhere today" are different claims and almost every French alert is the second one.
- **Loading is viewport-bounded and capped.** `/api/transit-fr/vehicles` answers one box no wider than **6°**, snapped outward onto a shared grid so neighbouring views share a cached answer, fetching at most **16 feeds** and returning at most **6,000 vehicles**; both truncations are reported to the client and surfaced in the layer's row. Feed bodies are cached 12 s (French feeds republish every 10–60 s), viewport answers 8 s, a failing feed backs off for 90 s, and its last-good fixes are served for up to 90 s and marked `stale`. Above ~300 km camera altitude the layer fetches **nothing** and shows zoom-in guidance instead of fanning out across the country.
- **What the layer shows is the operator's own value, and what it doesn't have it doesn't invent.** Position, bearing, speed, stop status and occupancy pass through unchanged. A vehicle whose feed reports **no bearing** is drawn as a disc, not a chevron pointing somewhere plausible. Glyphs **glide between two consecutive reported fixes** rather than jumping, so the scene renders up to one poll interval behind live and never extrapolates past the newest fix; the card always prints the age of the real fix, not of the glyph. `route` is the feed's `route_id`, unwrapped from its NeTEx envelope where it has one (`ATOUMOD003:Line:6xC5:LOC` → `6xC5`) and left verbatim where the publisher uses an opaque internal key. Each vehicle is drawn with the **icon for its class** — a bus as a bus, a tram with its pantograph, a river shuttle as a boat — because an earlier pass at hand-drawn plan-view silhouettes was internally consistent and unrecognisable. Twelve of the thirteen classes use a **Material Symbol** (Apache-2.0, see `licenses/material-symbols/`); `aerial` uses **Maki**'s `aerialway` (CC0, see `licenses/maki/`), because Material's `cable_car` is an interface glyph that reads as a building at 22 px and Maki draws the cable the cabin hangs from. Those icons are FRONT views, so they are never rotated; the operator's bearing is drawn instead as a small wedge ORBITING the icon on a second billboard, and a vehicle publishing no bearing simply has no wedge. **Speed and occupancy are advertised by almost nobody**: measured across all 148 queryable feeds on 2026-08-31, 84% of vehicles carry a bearing, 50% a speed and **9% an occupancy** (Palm Bus, SudLib and TCAT essentially alone). Each is drawn only where the operator sent it, and none is presented as a feature of the layer.
- **The line under a clicked vehicle comes from two feeds, and each says which.** A live position answers *"a bus is here"*; the next question is *"where is it going"*, and that answer is in two other resources of the SAME dataset. `/api/transit-fr/trip` resolves both: the **trace, the line's public name and its own colour** from the network's static GTFS, and the **ordered stops of the run with the operator's predicted times** from the network's GTFS-Realtime **TripUpdates** feed. `config/pan_gtfs_static.json` (built by `npm run transit:static`, 196 KB, URLs only — no geometry) is the map to them: measured 2026-08-31 all **142 datasets that publish vehicle positions also publish trip updates**, and every queryable feed has a static sibling with a conversion (148 at that build; the index re-probe of 2026-08-31 confirmed a third duplicate resource, so the shipped count is 147). Where the trip join fails the layer still draws the LINE from `route_id` alone and says the stops are not listed — the two halves degrade separately because they come from separate feeds.
- **`shapes.txt` is never downloaded, because the PAN already converted it.** A line's geometry lives in `shapes.txt` and its stop sequence in `stop_times.txt`, and those are the two largest members of a French GTFS archive by a wide margin — measured 2026-08-31 on Normandie's, **36.7 MB and 13.3 MB compressed**, expanding to 160 MB and 192 MB. Neither can be shipped, cached per network at build time, or parsed in a browser. The PAN converts every archive it hosts to **GeoJSON** and serves the result from a CDN with `shapes.txt` already joined to `routes.txt`, plus every stop point keyed by `stop_id`. Bordeaux TBM's is **13.3 MB fetched in 0.6 s**, indexed server-side to 124 routes / 532 traces / 7,385 stops in 0.8 s, simplified from 451,336 to 98,696 points (Douglas–Peucker at 2 m, invisible under a camera that must be below 300 km for the bus to exist on screen) and cached to `.gev-cache/pan-gtfs-geo/` at 2.5 MB. A first click on a network costs **0.87 s**; every later one costs **18 ms** and a 20 KB answer. Two things this cost measuring: the conversion URL is **derived from the resource id and not read from the catalog** — ten vehicle feeds across seven archives carry no `conversions` block and all seven derived URLs served content when probed — and it must be requested with `Accept: */*`, because asking the PAN for `application/geo+json` makes it answer **HTTP 500** (measured against resource 83024).
- **Which of a line's traces a run is on is MEASURED against that run's own stops.** A French bus line publishes several shape variants — Bordeaux's Lianes 7 has six, Lianes 35 has nine — and the conversion carries `route_id` but drops `shape_id` and `trips.txt` with it, so nothing in it says which trip uses which. The choice is therefore made against evidence the realtime feed does publish: the variant on which **every one of the trip's stops** lies, scored by the WORST stop rather than the average (a variant carrying 33 of 34 stops and missing the 34th by a kilometre is a different branch, and an average hides that). Measured against all 897 of TBM's running trips on 2026-08-31, **897 matched**, at a median stop-to-trace offset of **3 m** (p90 8 m, worst 40 m). When nothing holds every stop within **120 m** the layer draws the **whole line** instead of one run of it and the card says so — *"this is the line"* is a weaker claim than *"this is the run"*, and the drawing has to make clear which one is being made.
- **The stop list is live, and where it is missing that is the publisher's silence, not a decoding gap.** TripUpdates give the trip's stops in order with the operator's own predicted arrival and departure and a schedule deviation per stop; the approached stop comes from the vehicle's own `current_stop_sequence`, so a late bus still points at the stop it is heading for rather than the first one whose prediction has expired. `delay` is a protobuf **`int32`, not a zigzagged `sint32`** — read with the wrong wire type a bus running 19 s early decodes as 9.2×10¹⁸. Sampled across all 148 queryable feeds at 22:12 local on 2026-08-31 (off-peak: 54 networks reporting, 1,198 vehicles): **91.5% of the fleet publishes a `trip_id`** and 91.1% a `route_id`, and **58.5% joins to a trip update carrying stops**. That last gap is network-shaped, not fleet-shaped — **36 networks (518 vehicles) join 90%+ of their own fleet**, while 7 networks (313 vehicles) join none because their trip-update BODY is near-empty: Transvilles published 0 trips against 81 running vehicles, Rouen's three Astuce feeds 3 trips against 135, TaM 2 against 46. A vehicle-position body is also never decoded for trip updates and vice versa: the two readers are separate, so a 15-second viewport poll never parses TBM's 1.3 MB of stop-time predictions to draw 300 KB of positions.
- **Bison Futé DATEX II — the same roads, measured instead of modelled.** France's non-conceded national road network (the motorways and trunk roads the DIR operate directly, as opposed to the conceded ones Vinci/APRR/Sanef run) is published as DATEX II 2.0 over plain HTTP, keyless, under Licence Ouverte 2.0. Two publications, answering different questions: **`TRAFICOLOR-DIR`** gives a `trafficStatusValue` per site — 2 026 sites across sixteen traffic-management centres, refreshed every **60 s** at Bordeaux, Toulouse, Lyon and Limoges, 120 s at Rouen and Caen, 180 s in Brittany and Lorraine, 360 s at Marseille and Saint-Étienne — and **`QTV-DIR`** gives `vehicleFlowRate` (veh/h) and `averageVehicleSpeed` for every counting station, one snapshot every **six minutes** over a six-minute window (`publicationTime` 22:24 covers 22:24–22:30; the next is 22:30). This is the app's only source of an actual **vehicle count**: TomTom's flow tiles carry a ratio of current to free-flow speed and no number of vehicles at any price, and on a build with no `TOMTOM_API_KEY` the traffic layer runs its simulation, which makes this the only measured congestion data the globe can show.
- **The geometry is built at build time, because `refDir.csv` is not a referential.** The two live streams carry site IDENTIFIERS and no coordinate; the only geometry on the server is `QTV-DIR/refDir.csv`, and it has three traps. It is in **Lambert-93** (EPSG:2154, projected metres), so `scripts/lib/lambert93.mjs` reprojects it — deriving `n`, `C` and `Ys` from the projection's defining parameters and asserting them against IGN's published NTG_71 values rather than pasting constants, because a typo in a pasted constant is a silent kilometre. It is **regenerated every six-minute cycle and its row set moves** — 1 197 stations in one cycle and 1 192 in the next, measured 2026-08-31 — so a client reading it live would watch segments blink out for reasons that have nothing to do with the road. And it **lies about its own shape**: the header declares twenty columns and every row publishes nineteen (`code_insee_commune` is absent), so a reader that zips rows against the header shifts every field from the fourth onward, reads `nb_voies` as an easting, and concludes most of the network is unlocatable. `scripts/build-datex-traficolor-sites.mjs` reads positionally, validates against the CRS's area of use, and UNIONS each run with the committed file: `config/datex_traficolor_sites.json`, 485 KB, **1 958 sites of which 1 587 are located** — 608 of them full SEGMENTS, **975 km** of national network.
- **A row with no coordinate is not a row with no geometry — 743 of the 1 587 positions come from a kilometre post.** The French road network is addressed by POINT REPÈRE: a numbered post, a département, a carriageway and an abscissa in metres past it (`76PR91D` + 800 m). 525 of the referential's 1 367 rows publish no `x_deb` at all, and **155 of them publish that address instead** — including all 115 stations of DIR Ouest, which had never been drawn. Every post of the non-conceded network is published with its Lambert-93 coordinates in a second open dataset, the [Bornage du réseau routier national](https://www.data.gouv.fr/datasets/bornage-du-reseau-routier-national) (51 940 posts, Licence Ouverte 2.0), so `scripts/lib/rrnBornage.mjs` resolves one against the other. **The join is calibrated on every build, not trusted**: 832 stations publish an address AND a coordinate, and resolving theirs disagrees with the DIRs' own answer by a median of **3.8 m** (p90 7.2 m, max 64 m, 99.8 % within 25 m) — the DIRs derive their published coordinates from this very referential. That number is recomputed and stored in `bornage.calibration` each run, so an edition that stopped agreeing would move it in the build log before it moved a station on screen. The abscissa is deliberately NOT applied to referential rows: doing so makes the same comparison p50 402 m, because the DIRs snap their own coordinate to the post and drop it. A bare PR that matches posts in several départements — the N12 has five at PR 56, 439 km apart — is refused unless the site's own identifier names one of them, a regularity measured at 799 agreements against 2 exceptions before it was used for anything.
- **Four dark cities turned out to be addressed, not unlocatable.** Nantes, Rennes, Saint-Brieuc and Lorient–Vannes publish 619 live states under identifiers that appear in no referential row — which is why they were drawn nowhere — but those identifiers ARE point-repère addresses: `35A0084T096_00D` is département 35, route A84, PR 96, abscissa 0, right-hand carriageway. **602 of them resolve against the bornage**, and the four move from `roadStatusCoverage.js`'s dark list to its showcase list. Here the abscissa IS applied — 133 pairs of sites differ by nothing else, so dropping it would draw 266 sensors on 133 points — and it is interpolated along the chord to the next post, clamped there rather than walked past it. **Lille stays dark, and that is a finding too**: its 357 site ids were tested against the bornage both ways they can be read, and the only reading that fits at all puts DIR Nord's A1 sensors at PR 12–30, which is département 95, inside Île-de-France. A grammar that has to be wrong to parse is not the grammar.
- **And the segments follow the surveyed centre of their own carriageway.** The referential gives a counting station two endpoints and nothing between them, so every segment was drawn as a straight chord. Threading the kilometre posts lying between the two ends was the first answer and it could not carry the layer: **the median segment is 948 m long and the median post interval 1 000 m**, so 643 of 842 segments contained no post at all and stayed straight. Measured 2026-09-01, the drawn line sat a median **56 m** from its own tarmac, 142 m at p90, with **411 segments past 25 m** and 145 past 100 m — on the Bordeaux rocade, a line cutting the inside of every curve. The fix is the dataset next door: [Liaisons du réseau routier national](https://www.data.gouv.fr/datasets/liaisons-du-reseau-routier-national) (DGITM, Licence Ouverte 2.0, the same archive the bornage ships in) publishes **56 205 polylines, 1.66 M vertices, one per PR interval, at a mean 26 m between vertices**. **The join needs no geometry at all**: each section NAMES the two posts it runs between (`nom_plo_in` = `01PR122DC`, the address `parsePrAddress` already reads), so it is placed in the same cumulative-distance space the bornage index is sorted by — and the coordinates are then free to be CHECKED rather than trusted. Over 33 483 joined sections the polyline's own ends sit **p50 0 m, p90 0 m, p99 0 m** from the posts they name: the two files are cut from the same survey. `dist_deb`/`dist_fin` look like the same key and are not — they restart at zero in every département (the A63's right carriageway publishes `33:0-250`, `40:0-550`, `64:0-140`) while `cumul` runs continuously, so keying on them interleaves three départements into one line. `portee` is `D`/`G`/**`U`** where the bornage writes `D`/`G`/**`I`**; mapping that is the whole of the carriageway half of the join, and skipping it loses every undivided national road in France. **589 of the 608 real segments trace** (96.9 %), for 5 326 vertices against the 1 216 endpoints they replace, after Douglas–Peucker at **4 m** — under the width of a traffic lane, so nothing a camera resolves is removed. The committed file goes from 364 KB to **485 KB** (29 KB to 52 KB gzipped). The 19 that do not are slip roads and unnumbered axes the PR referential does not address; they keep the post threading, or the chord, exactly as before. The guards refuse to shape rather than guess: a section drawn more than 50 m from the posts it names is dropped (without it one section joins a post 13.8 km away), an endpoint more than 150 m from any post of the road it names is refused, and a trace running more than 3× the straight line between its ends is refused — the ring-road case, where the two ends sit either side of the A630's closing point.
- **234 of the 842 "segments" were points wearing a segment's shape.** Their referential row publishes `x_deb` equal to `x_fin`, and they were being written as four-number segments and handed to Cesium as zero-length ground polylines — geometry it cannot stroke. They are now written as single points, which is what makes the renderer draw them as the 25 m stub a positioned station with no extent deserves. That is why the segment count falls from 842 to **608** while nothing is lost: the difference was never 234 roads.
- **Where it is blind, and the two different reasons.** **Île-de-France has no publisher at all**: the DIRIF appears in neither publication — zero counting stations inside the region's bounding box, zero agglomeration directories — verified three ways on 2026-08-31, and data.gouv.fr's only DIRIF dataset is a 2008–2011 count archive. Separately, **Lille and Nancy–Metz publish a live colour for 431 sites whose position nobody publishes and no address can recover**: DIR Nord's ids are operator codes rather than point-repère addresses, and 70 of DIR Est's 72 stations carry neither a coordinate nor a PR. That list used to include Nantes, Rennes, Saint-Brieuc and Lorient–Vannes; the point-repère join lit all four on 2026-09-01. Those are not the same statement, and `src/data/roadStatusCoverage.js` keeps them apart so an empty view over Lille reads "357 live road states published under site ids that are neither a referential row nor an address" rather than looking like a bug. Its claims are cross-checked against the built index by `roadStatusCoverage.test.mjs`, so a DIR that starts publishing coordinates — or an identifier that turns out to be an address, as Brittany's did — fails the suite instead of leaving a city wrongly dark.
- **This layer is brightest exactly where Transit FR is dark.** Marseille (192 drawable segments), Nantes (184), Rennes (177), Bordeaux (169), Toulouse (128), Lyon (109) and Saint-Étienne (100) publish no live bus position at all; Paris, where Transit FR has its one Rosny-sous-Bois shuttle, publishes no road status at all. Neither layer covers urban France; together they nearly do, and both say so rather than showing an unexplained blank.
- **One national snapshot, not one fetch per viewport.** `/api/road-status-fr/segments` holds the whole country — ~2 000 status sites and ~1 600 drawable sites, 608 of them full segments — refreshed at most once every 60 s (and the 1.2 MB flow snapshot at most once every 6 min), then filters it in memory, which is why its box ceiling is 20° rather than the 6° the transit proxy must enforce. The sixteen centres are read settled, so one being down greys one city rather than blanking the country, and every failure is named in the `feeds` array the row renders. The browser never talks to `tipi.bison-fute.gouv.fr` directly: the host serves **no TLS and no CORS header**, so an https page could not read it even if it were permitted to.
- **What is drawn is what was published, including the absence.** A segment's colour is the operating centre's own `trafficStatusValue` and is never derived from the count — a located station no centre watches stays grey and the legend says "Not reported" rather than folding it into free flow. Where two centres report one site the WORSE state wins, because a road called free by one and congested by another is not a road anyone should be told is free. Flow and speed are labelled **6-min average** on the card, never as an instantaneous reading. A station that counted nothing prints "no vehicle counted in the last 6-min window" instead of "0 km/h" — 114 of 1 192 stations at 22:30 CEST, which is a fact about the hour, not a jam.
- **ODRÉ éCO2mix.** Keyless. RTE's own `data.rte-france.com` API carries the same figures behind an OAuth2 client-credentials account; **ODRÉ** (Open Data Réseaux Énergies, operated by RTE with GRTgaz and Teréga) republishes them on an Opendatasoft instance under Licence Ouverte 2.0 with no credential, so the layer works on `git clone`. `/api/energy-fr` fetches `eco2mix-national-tr` and `eco2mix-regional-tr` in parallel — with `Promise.allSettled`, so a regional outage does not blank the national gauge — and projects the pair down to ~7.8 KB, cached 4 minutes in memory and on disk. Measured 2026-08-27: national 200 in 0.30 s, regional 200 in 0.23 s, all 12 régions sharing one `date_heure`, and the newest measured point at 07:45Z against a 07:53Z wall clock — an ~8 minute publication lag on a 15-minute product. Regional publication can also trail national by a step, so the proxy keeps the newest measured row **per région** rather than taking every row at the newest timestamp; a lagging région then shows its own last state, stamped with its own time, instead of blanking.
- **The rolling window is padded with the future, and the padding is all-null.** `ORDER BY date_heure DESC` alone returns *tomorrow's* rows, which carry `prevision_j1` and nothing else — every measured field is null, so a client reading "the latest row" shows an empty mix. Both upstream queries filter on `consommation IS NOT NULL` and the projection filters again (`src/data/eco2mixFeed.js`, pinned in `eco2mixFeed.test.mjs` against captured payloads).
- **The same field is an int nationally and a string regionally.** `pompage` is `-66` in the national row and `"0"` in the regional one; so are `stockage_batterie` and `destockage_batterie`. Every numeric read goes through one coercion that also refuses to fold `''` and `null` to `0` — "not published" and "zero megawatts" are different facts. The two filière splits do not match either: national separates `gaz`, `fioul` and `charbon` where regional rolls all three into `thermique`. They are kept as two tables rather than reconciled, because inventing a regional gas figure RTE does not publish would be fabrication.
- **`ech_physiques` is consumption MINUS generation, so a net exporter is NEGATIVE.** Verified arithmetically against the captured national row: 50 831 MW of filières plus −66 MW of pumping against 47 132 MW consumed, and the row's own `ech_physiques` is −3 633. The layer inverts this once, at the paint boundary, and restates it as an export figure in `getStats()` and for the analyst — a HUD reading "+6 478" for a région that is *importing* would be exactly backwards.
- **Commercial balances are not physical flow, and they do not sum.** The five `ech_comm_*` fields are commercial nominations between market areas; the captured row nets −2 893 MW commercially against −3 633 MW physically. Both are published and both are correct, so the layer draws the commercial figures on the border arcs and reports the physical net separately under its own name. `ech_comm_allemagne_belgique` is **one field for two countries** and stays one arc, labelled with both.
- **The border arcs are country-to-country balances, not cables.** Their endpoints are country reference points, deliberately **not** interconnection sites: anchoring a market-area balance at Calais or Baixas would claim a precision about physical routing that the field does not carry. A border at 0 MW is drawn as no arc at all.
- **Régions are painted on département geometry, and Corse is never painted.** There are no bundled région polygons, so the 96 département shapes already carried for Vigilance are grouped by région (2016 boundaries, matching `code_insee_region`) and every département inherits its région's value — a presentational grouping, so no label ever names a département. éCO2mix régional covers **12 metropolitan régions**; Corsica runs on its own system and is absent upstream, so 2A and 2B are held permanently hidden rather than inheriting a neighbour's colour or defaulting to zero. Carbon intensity is national only — RTE publishes no regional CO₂ content, and none is painted.
- **Open Data EDF — the generating fleet.** Keyless, and deliberately not through the API most of the web still links to: opendata.edf.fr has migrated from Opendatasoft to Koumoul's data-fair, and while the ODS compatibility layer still answers `/api/explore/v2.1/…/records`, its catalog, facets and v1 search routes now return **410** or the portal SPA's HTML 404 (measured 2026-08-27). `/api/edf-plants` therefore uses the native `data-fair/api/v1/datasets/{slug}` and `…/lines` routes — which also carry each dataset's DESCRIPTOR, so the layer reports every file's own licence and reference date instead of hard-coding a date that would silently rot. Six requests, ~159 KB, 0.21–0.33 s each, projected to one ~36 KB document of 79 sites, cached 24 hours in memory and on disk. The three files are fetched with `Promise.allSettled` and merged **per filière** over the previous cache: a nuclear outage must not report that France has no reactors.
- **This is EDF's fleet, not France's, and nothing in the layer implies otherwise.** All 126 rows carry `perimetre_juridique: EDF SA`. The hydro file says so itself — *"sur les plus de 400 installations hydrauliques exploitées par EDF, seules les centrales d'une puissance supérieure à 100 MW sont présentes"*, plus an exception for those whose secondary reserve reaches 20 MW, which is why five plants below 100 MW are in it (Grandval, 74.1 MW against 20 MW of reserve, is the smallest). No CNR or SHEM hydro, and no Engie or TotalEnergies CCGT, is in scope. Nuclear is the one filière where the operator is the country, so those 56 reactors are the French fleet. Corse and the îles du Ponant are outside all three files' declared geographic scope, so nothing is drawn there.
- **Three files, three vintages, so there is no single "as of".** Nuclear is a *vision consolidée au 31/12/2025*; hydraulic and fossil-fired are *au 31/12/2023* (the portal's own `temporal` field, which agrees with that sentence in all three descriptions). Their 80 094 MW sum is therefore a capacity that never existed at one instant — every site is stamped with its own file's date and the layer reports the range. The nuclear file's newest reactor entered service in **2002**, so the EPR commissioned at Flamanville after that vision closed is not in it.
- **Installed capacity is not production, and a row is not a site.** `puissance_installee` is nameplate power: a 5 460 MW disc at Gravelines is what the site can produce, not what it is producing — `/api/energy-fr` owns that question. The nuclear and thermal files publish one row per UNIT and repeat the site's coordinate on each, so rows are grouped by `centrale` (56 reactors → 18 sites, 19 units → 10) rather than stacking six markers on one pixel; the hydro file publishes one row per PLANT and says nothing about its turbine count, so hydro sites report **no** unit count rather than "1". `reserve_secondaire_maximale` is likewise a site figure repeated on every unit row — all 28 multi-unit sites publish one identical value — so it is read, never summed: Cattenom offers 60 MW of reserve, not four times 60.
- **The two coordinate conventions disagree, and one of them is inverted.** The hydro file publishes `coordonnees_x_wgs` as the **LATITUDE** and `coordonnees_y_wgs` as the longitude; read the usual x=longitude way, Grand-Maison lands off the coast of Somalia. The nuclear and thermal files instead publish one `point_gps_wsg84` string (WGS misspelt WSG) formatted `"lat, lon"`. Both are normalised in `src/data/edfPlantsFeed.js` and every parsed point is checked against a metropolitan-France box, so a swap fails loudly instead of drawing a power station in the Indian Ocean. The three files also spell a région three different ways — accented title case with no INSEE code in hydro, uppercase unaccented with one in the other two — so records keep whichever spelling their own publisher used and joins go through a folded key.
- **Five EDF sites appear on the Réseau gaz layer too, and neither publisher is wrong.** That layer draws ODRÉ's register of the 14 centralised gas-fired stations whoever operates them; this one draws EDF's own fossil-fired file whatever it burns. Measured 2026-08-27, the overlap is exactly the five EDF gas sites — Martigues (0.09 km apart), Bouchain (0.55), Blénod (0.12), Montereau (0.60), Gennevilliers (0.15) — and the two disagree slightly on capacity there: 585 against 575 MW at Bouchain, 427 against 430 at Blénod, 203 against 210 at Gennevilliers. Nothing is de-duplicated between them: neither set contains the other (ODRÉ carries Engie, TotalEnergies and Uniper plants EDF's file cannot claim; EDF's file carries the coal and fioul units a gas register does not), and dropping one publisher's figure would hide that they disagree.
- **A dam is not a power station.** The bundled Barrages layer draws OpenStreetMap dam STRUCTURES; measured, only 3 of these 51 hydro plants sit within 3 km of one. Nothing is de-duplicated between the two layers, because a barrage and the usine it feeds are different objects from different sources.
- **Barrages — the French half is a direct OSM extraction, the world half is the older snapshot.** The pack shipped 704 features for the whole planet until 2026-09-01, decoded out of an Open Infrastructure Map POWER-PLANT layer filtered on a dam tag: **44** of them were in France, so in a France fork the row lit up on nothing. `npm run dams:pack` now queries Overpass for `waterway=dam` / `man_made=dam` / `building=dam` across `ISO3166-1=FR` — the whole Republic, so Réunion, Guyane, les Antilles, Mayotte, la Nouvelle-Calédonie and la Polynésie are in — and merges the result with the 660 world features the old snapshot had, superseding by OSM id. Total **6,189** (1.9 MB), rebuilt in ~90 s and byte-for-byte reproducible. This is OSM's idea of a dam, not a register: France's own ROE lists ~100,000 obstacles à l'écoulement and is an order of magnitude larger.
- **Most of what OSM calls a dam in France is a farm weir, and the layer grades rather than hides that.** 4,579 of the 6,189 features carry no name, no height and no operator; 148 carry a height and 972 are hydroelectric. `damTier()` in `src/data/damsPack.js` puts a feature in **Grand barrage** when it is ≥ 15 m high (the ICOLD threshold), or generates electricity, or is named and ≥ 300 m long — 1,060 features — then **Barrage nommé** (550) and **Seuil & petit ouvrage** (4,579). The tier drives the dot size, the colour, the label range, the row chips and the legend, exactly as the airport tiers do. `spanM` is measured off the mapped geometry and is deliberately NOT a ranking clause on its own: at 300 m it admits 286 French features of which 165 have no name, because the long objects in this file are canal embankments, not big dams.
- **Barrages vs Petite hydro vs Groupes de production: measured, the overlap is 5%.** The obvious worry about a 5,529-feature French dam pack is that it restates the hydro layers next to it. Measured 2026-09-01 against the 5,434 features inside the metropolitan box: **274 (5.0%) sit within 200 m of a placed `fr-hydro-plants` installation** (207 within 100 m), and **21 within 200 m of an RTE hydro site** (27 within 500 m, 83 within 3 km). 95% of the pack has no counterpart in either layer — they are seuils, digues d'étang and barrages de retenue that no production register lists. Where the two DO coincide they coincide almost exactly, a few metres apart, and the reason is in the hydro pack's own build: 371 of its 998 placed installations were positioned by joining onto an OSM power plant (`placement: {osm-plant: 371}`), so both layers inherit the same coordinate for the same site. **Nothing is de-duplicated, deliberately** — dropping Génissiat, Monteynard or l'Aigle from a dam layer because a production layer also draws a marker there would empty it of exactly the barrages a reader came for, and the two objects are genuinely different: one is a wall, the other is a turbine hall. The dam card stays on the wall's own facts (height, span, material, crest) and only prints an output where OSM tagged one on the dam object itself — 38 French features out of 5,529.
- **The world half of the Barrages pack IS power stations, and that is the price of not emptying it.** The 660 non-French features are the old Open Infrastructure Map extraction: power-plant outlines that carry a dam tag, not dam structures. They are kept so the layer draws something outside France, they pass through the same projection and card as the French half, and `coverage: 'fr'` is the taxonomy telling a reader not to mistake them for coverage.
- **Météo-France's real-time station network.** Keyless, and it takes four of the publisher's files to say one thing. The *liste des stations du réseau d'observation temps réel* is eight columns and **2 144 identical rows** — identifier, WMO number, name, position, altitude, opening date, pack — and says nothing about what any station measures. That is in `fiches.json`, a **191 MB** inventory of every parameter every poste has ever measured, dated one instrument at a time, joined at authoring time because no browser can fetch it. `POSTES_MF.csv` supplies the commune, the lieu-dit and the poste type. The SYNOP station list supplies the fourth fact, badly (below). Rebuilt with `npm run meteo:stations`; the shipped pack is 644 KB and carries fourteen instrument booleans per station.
- **A French weather station usually is not a weather station, and that measurement is the layer's palette.** Against Météo-France's own inventory: **2 084 stations measure temperature and 2 068 measure rain, but only 845 measure wind and only 234 measure pressure.** **1 254 of the 2 144 — 58 % — measure temperature and rain and nothing else**; only **228** measure the five parameters the phrase "weather station" means to a reader. Colour is therefore capability, not decoration, and the card names every instrument in words because colour alone must never carry the meaning.
- **The instrument list is anchored on hourly readings, never keyword-matched.** The publisher's vocabulary is **254 parameter names** for this network and most are DERIVED statistics — `NOMBRE DE JOURS AVEC TX>=35°C`, `CUMUL DES DJU SEUIL 18 METHODE CHAUFFAGISTE`. Matching on "TEMPERATURE" would count a degree-day accumulator as a thermometer; matching on "VENT" would count `MOYENNE DECADAIRE DE LA FORCE DU VENT`, present on **879** stations, as an anemometer when only **845** have one. A parameter carrying a `dateFin` is a decommissioned instrument and is not read.
- **Météo-France's SYNOP station list names 62 stations; the SYNOP archive it describes contains 190.** Boulogne-sur-Mer, Le Touquet, Dunkerque, Dieppe, Beauvais-Tillé, Ouessant-Stiff and 123 others write an open hourly observation the list never mentions, and every one of the 190 resolves to a station in the real-time list. It fails the other way too: **CAP CEPET (07661) is named in the list and has written nothing all year.** The pack ships `synop` (named) and `live` (publishing) as separate fields, and the layer's ring counts the second.
- **Every popular SYNOP mirror froze on 2026-01-15T09:00Z.** Measured 2026-09-02 on both `public.opendatasoft.com` and the Toulouse Métropole instance that data.gouv.fr's own dataset links to. Météo-France's S3 archive was written that same morning and carries observations to the previous hour. Anything reading a mirror for "current French weather" has been serving a seven-month-old number since January — which is why the proxy pays for the archive instead.
- **The live observation costs 22 MB server-side, lazily, once an hour.** `OBS/SYNOP/synop_<year>.csv.gz` is the running year in one file and a SINGLE gzip member, so no range request can reach its tail; there is no smaller live product without an API key. `/api/meteo-stations/observations` therefore fetches it whole, streams 364 444 rows through a reducer that keeps 190, and serves ~38 KB. Nothing is fetched until a reader opens a station card — a visitor who turns the layer on and never clicks costs zero requests — and `/status` reports the cache without ever filling it.
- **Seven stations in the real-time list are closed, and the layer says so instead of tidying them away.** MARSILLARGUES since 2026-01-01, BASSE-TERRE GUILLARD since 2026-02-11, DESHAIES GENDARMERIE since 2024-10-01, ST JOSEPH-CIRAD and TAN ROUGE-CIRAD since 2023-03-29, DEMBENI and MAMOUDZOU_SAPC since 2025-04-01. Météo-France's own metadata records the closure and its own real-time list still carries the station. They are drawn hollow and the card leads with the date. Six more — ALBA LA ROMAINE, SOULAINES, TARASCON, PIOGGIOLA, QUERCITELLO, MURAT SUR VEBRE — appear in the real-time list and in no metadata file at all; their `fam` is `null`, not `[]`, because "nobody documented this" and "this measures nothing" are different facts.
- **What the layer refuses to draw.** The **12 347 closed climatological postes** (`POSTES_MF.csv` runs back to **1806** and only 2 404 are open) — drawing them would say the network is five times its real size. The **699 *stations complémentaires*** run by the DGPR, the DIR routes, the DREAL, EDF and INRAE — published separately, absent from the real-time list, and not expertise-guaranteed by Météo-France. And the **Infoclimat / StatIC** network: 1 138 French stations of which **553 are CC BY-NC**, so more than half the file forbids commercial reuse station by station, which is a licence trap rather than a data source.
- **This layer overlaps Vigilance météo and nothing is reconciled.** Vigilance paints a WARNING per département; this paints the instruments. A département can be orange for wind and hold not one station that measures wind — 60 % of the network cannot — and both statements are correct, because a vigilance colour is a forecast over an area, not a reading at a point.
- **The bundled buoys are a US network, and there is no French sea state on the globe yet.** The `marine-buoys` layer is NOAA NDBC, whose report carries 861 stations of which **8 sit inside the metropolitan French box — and all eight are UK Met Office or Irish moorings in the Channel and the Western Approaches**. Météo-France's own SYNOP open dataset is 62 LAND stations. The French sea-state network is **CANDHIS** (Cerema, ~40 real-time houlographes, métropole + outre-mer), published under **Licence Ouverte v2.0** with a documented REST API at `https://candhis.cerema.fr/API/v1/` whose `getCampListeTR.php?type=N` returns the latest hourly H1/3, Hmax, TH1/3, peak direction, spread and sea temperature for the whole network of one sensor type in a single call — a 1:1 fit for the card the NDBC layer already writes. The one gate is an access key, requested by email from `candhis@cerema.fr` (name, activity domain, structure type); the API is GET-only, key in the `Authorization` header, with a daily request quota. SHOM/REFMAR was considered and is the wrong subject — tide gauges measure sea LEVEL, not sea state — and EMODnet Physics, though keyless, is a per-platform research catalogue whose French wave data originates from CANDHIS anyway. **Nothing is blocked on a licence here; it is blocked on an email.**
- **NOAA NDBC marine buoys.** Keyless. `/api/ndbc` fetches one ~106 KB text report that carries the latest observation from every reporting station in the network (892 stations measured 2026-08-26), caches it 10 minutes in memory and on disk under `.gev-cache/ndbc.json`, collapses concurrent refreshes into one upstream pass, and serves the last good report during an outage. No bounding box is needed: one fetch covers the globe. The 10-minute TTL is courtesy, not quota — stations report every 10–60 minutes and the observed spread of stamps within one file was 0.2–3.0 h (median 0.8 h), so polling faster would re-download bytes that cannot have changed. **The network is sparse, and the layer says so rather than hiding it:** of those 892 stations, 21% carried a wave height, 57% a sea temperature and 72% a wind reading; only 533 reported wave height *or* sea temperature at all. A station with no wave sensor renders neutral grey and omits the line entirely — it is never drawn as a calm sea, and a genuine `0.0 m` reading stays visually distinct from an absent one. The layer's control chip carries the measured/total split (e.g. "491 of 893 measuring sea"). Observations older than 12 hours, and any stamped more than an hour into the future, are dropped before they reach the client. NDBC serves outage notices as HTML, so a body that does not parse as an NDBC report is rejected outright rather than cached as a legitimately empty ocean.
- **French shared mobility (GBFS).** The same national access point, a different half of it: 165 `gbfs` resources, all of them `vehicles-sharing` datasets. Measured 2026-08-27 — **135 distinct systems** once the catalog's own duplicates are removed, holding **~15,500 operator dock stations and ~40,600 free-floating vehicles** (bikes, e-bikes, scooters, mopeds, shared cars). Feeds are JSON rather than Protocol Buffers, and 150 of the 165 point at a `gbfs.json` **auto-discovery** document rather than at a data file — which is why they are served by a new `/api/shared-mobility-fr` proxy rather than by the older `/api/gbfs` one, whose eight-host allow-list and `station_*.json`-only path filter are the right shape for the registry-driven Bikeshare layer and the wrong shape for this.
- **This source is an INVENTORY, not a track.** The GBFS spec: *"Vehicles that are part of an active rental MUST NOT appear in this feed."* A vehicle being ridden is invisible — it disappears at unlock and reappears where it is parked. Measured on Lime Paris over 127 s: 49 vehicles disappeared, 39 appeared, 6,702 stood still, and the 8 that "moved" travelled 30–45 m, which is GPS drift on a parked bike rather than a journey. Nothing here is interpolated the way the transit layer interpolates a bus; there is no journey published to interpolate. Positions come from an IoT module in each free-floating vehicle (the feeds carry its own `current_range_meters`), and from the station's known fixed position for a dock network. The spec also requires the vehicle identifier to be **rotated after every trip**, so a returned vehicle reappears under a new id and no rider can be followed between trips.
- **Freshness is uneven, and is shown per object rather than per poll.** Measured 2026-08-26: Lime republishes every ~50 s (median fix age 50 s); Dott declares a 300 s `ttl` but its median fix is 8 minutes old with a tail past 2 h 48; Vélib' station status runs ~26 minutes behind. The spec's own ceiling for these endpoints is 5 minutes, which several French operators exceed. The card therefore prints the age of the **vehicle's own last report**, never the age of the request.
- **Three separate redundancies are resolved before anything is drawn, all measured rather than assumed.** The rules live in `src/data/gbfsFeeds.js` and the verdicts are recorded — not silently dropped — in `config/gbfs_fr_systems.json`, so the index is also the evidence for why something is missing.
  1. **The catalog lists one system many times.** 23 of the 165 resources are duplicates: 17 share an identical resolved feed URL (Dott publishes one Paris feed as "France", "Paris", "Lyon", "Bordeaux", "OL Vallée" and "Bourgoin-Jaillieu"; Vélam Amiens and VéloMoove Pompey are each listed five times), 3 are the same network on a second host or GBFS version, 3 are an aggregator mirroring a small operator. Identity is the **set of places** a system reports, which is the only test that survives all of those — a URL comparison misses Vélo'v Lyon entirely, because JCDecaux and the Métropole publish its same 464 stations from different domains.
  2. **Four systems are already drawn by the Bikeshare layer** — Vélib', Vélo'v, vélÔToulouse and Le Vélo (TBM). They are excluded here rather than doubled, and the check runs against that layer's live registry (`bikeshareCoveredSystems()`) so adding a city there cannot silently start drawing it twice.
  3. **Free-floating operators republish the city's own parking bays as their "stations".** Paris requires it, so Dott and Voi each report ~13,000 bay positions of which 96–97% are also reported by the other — while running entirely different fleets. Those are not the operator's infrastructure and are **not drawn per operator**: 32,783 station rows across 12 systems are merged out this way, and the layer's control row says how many. The discriminator is measured (how many surviving systems report the same coordinate), not a name list. A whole-city SENTINEL row is dropped on the same grounds — Lime Paris publishes one station called "Paris Proper" with 999,999 docks holding its entire fleet.
- **Colour is a display convention, and is labelled as one.** GBFS has no brand-colour field — `system_information.json` publishes a name, a URL and a licence, never a livery — so the operator hue this layer draws is GEV's, not the operator's. Two rules keep that honest, both in `src/data/mobilityOperators.js`: the ~15 operators running several French systems (Lime, Voi, Dott, Pony, Bird, Tier, Citiz, Clem', YEGO, Cityscoot, Leo&Go, plus the four docked networks the Bikeshare layer draws) are **pinned by hand** to a slot no other pinned operator can take, so one operator reads the same in every city; every other network's hue is **derived** from its published title by a hash and says so in the legend tooltip, which means two municipal networks *can* land on the same hue. The row legend names every operator in view, and the names — not the hue — are the authority. Vehicle SHAPE is a separate channel and comes from data: `form_factor` + `propulsion_type`, folded to six kinds in `src/data/gbfsFeeds.js`. A station keeps its fill for availability and carries the operator on its ring, so the one actionable number is never spent on ownership.
- **Bounds are observed and fenced, like the transit index.** A system's footprint is where its objects actually were when probed, with a Tukey far-out fence applied first and a ±0.5° slack at request time: a Villefranche-sur-Saône scooter reported over Nantes, 450 km from its network, would otherwise stretch that system across half of France and put a stray dot in every city in between.
- **Per-viewport caps are shared fairly.** `/api/shared-mobility-fr/objects` answers one box no wider than 3°, fetching at most 14 systems and returning at most 6,000 objects — allocated as an equal share per operator with the remainder redistributed, because Lime alone reports ~6,000 vehicles over Paris and a sequential fill would spend the whole budget on whichever operator happened to rank first. Both truncations are reported to the client.
- **BD TOPO is served at z15 and there is nothing above it.** Measured 2026-08-31 over the same 1.3 x 1.2 km window at Fourvière: z16 needs 12 tiles for 1,336 distinct buildings, z15 needs 4 for 1,335 of the same ones — same bytes, identical attributes on every building sampled, one missing at a tile boundary. IGN does not simplify the `batiment` layer between the two, so z16 buys nothing and costs three times the requests. z14 parses and has no `batiment` layer at all. The layer therefore reads z15, and a 6 km viewport costs ~49 tiles instead of ~165.
- **Half of France publishes roof altitudes and half does not, and it is not the half you would guess.** On z15 tiles captured 2026-08-31: Fourvière carries `altitude_maximale_toit` for 1,143 of 1,173 buildings (photogrammetry / corrélation); Montmartre carries it for **0 of 1,753** and La Défense for **0 of 314**, because Paris's buildings come from the cadastre with `methode_d_acquisition_altimetrique: "Interpolation bâti BDTopo"` and carry only a floor altitude and a height. A seating rule that assumes the roof altitude flattens Paris; one that only ever uses `hauteur` throws away the better measurement everywhere else. The layer runs both, counts them separately, and every card names which one placed that building.
- **`precision_altimetrique: 9999` is a sentinel, not a precision.** It travels with `methode_d_acquisition_altimetrique: "Pas de Z"` — 114 of the 1,753 buildings on the Montmartre tile, 67 of 314 on La Défense. Read literally it is a ±10 km tolerance that would validate any altimetric check ever written, so it is discarded before any comparison rather than clamped.
- **The altitudes are NGF-IGN69 and the globe is WGS84.** h = H + N, with N ≈ +44.6 m over Paris and +50.8 m over Grenoble (EGM96, `src/data/geoid.js`). Forgetting it sinks every French building 45 m into the terrain. Note the residual this leaves: NGF-IGN69 is tied to the RAF geoid, not to EGM96, so the absolute tie to WGS84 carries up to ~1 m of systematic offset — but the SAME correction is applied to every building, so their relative geometry is exact, which is what the eye reads.
- **A national survey and a global terrain do not agree, so the buildings are re-anchored per cell.** The rendered surface under France is Re:Earth's ~30 m mesh (or Cesium World Terrain with an ion token); BD TOPO's floor altitudes are surveyed. The layer measures the rendered surface **under each building** — `globe.getHeight` on the terrain triangles already resident, synchronously and with no network — takes the median difference against the IGN floors of the buildings in the same ~1.1 km cell, and shifts them all by it, keeping the fine relief IGN measured between neighbours while landing the block on the ground the user can see. The coarse DEM grid (~64 heights per viewport, at cell centres) is only asked for on a camera that has just teleported, where nothing is resident yet to read.
- **The measurement has to be under the building, and this is what happens when it is not** (fixed 2026-08-31, reported from Lyon). The first version sampled the surface once per ~1.1 km cell and differenced that one height against every building's own floor. On flat ground that difference is the datum error and the layer worked; on a hillside it is the *relief between the cell centre and the building*, and a 0.01° cell on the Croix-Rousse slopes spans 30–60 m of it. Every building in the cell was then lifted by the same wrong number — a whole block hanging in the air, with the block in the next cell sitting correctly on the ground. Sampling per building was assumed to be unaffordable; it is free, because `globe.getHeight` reads resident triangles rather than the network DEM the assumption was priced against.
- **What is left after the shift is absorbed by the volume, never by moving it.** A cell offset is one number and the mesh disagrees with the survey building by building, so each volume grows by whatever is left: the base reaches DOWN when the mesh is below the survey, the roof rises UP when it is above. Nothing floats and nothing vanishes into a hillside, and the floor altitude on the card is still the one IGN published, because the correction only ever lengthens the box — it never moves it. Beyond 60 m it stops: at that distance the ground sample is wrong (a coarse LOD, a cliff edge), and a 200 m skirt of wall is a worse artefact than the float it would hide. The layer reports the residual it had to absorb (`groundGapMedianM`, `groundGapWorstM`) instead of averaging it away.
- **`altitude_minimale_sol` is the low corner of a footprint, not the ground under its middle** — and BD TOPO publishes `altitude_maximale_sol` beside it wherever it publishes roof altitudes (Lyon, Marseille, Grenoble; the drop across a footprint runs 0 to 13 m on the captured tiles, median 1.9 m). A height sampled at the centroid measures the middle, so it is compared against the middle of the two. Comparing it against the low corner instead would read half of each building's own footprint slope as terrain disagreement — a systematic ~1 m lift on every hillside building, on top of whatever the terrain is really doing. Paris publishes neither, and Paris is flat: there the floor is the whole answer.
- **French gas system.** Keyless, four ODRÉ datasets under Licence Ouverte 2.0. Measured 2026-08-27: the NaTran (ex-GRTgaz) trace is 11,615 rows / 4.93 MB in 1.35 s, the Teréga trace 1,298 rows / 0.55 MB, the power-station register 98 rows, the injection register 854 rows. The proxy projects those 6.2 MB down to a 933 KB geometry document fetched **once per session** and a 331 KB register document, and caches them for a week and twelve hours respectively — the traces are republished about once a year. Cold 1.39 s / 0.32 s, warm 2.4 ms / 3.2 ms, under `.gev-cache/gas-fr/`.
- **The trace is a published simplification, not a pipeline location.** Both titles say *précis à environ 250 m*. Nothing is densified, smoothed or re-routed; the published segments are only concatenated where they already share an endpoint exactly (11,468 NaTran parts → 6,074 strokes, within a département so the one attribute either file publishes survives), and coordinates are rounded from ~15 decimals to 5 (~1.1 m, still 200× finer than the product's own stated accuracy). That rounding is also what reveals 165 published "lines" whose vertices are all one point.
- **Teréga's third ordinate is not a height.** Teréga publishes `[lon, lat, z]` where NaTran publishes `[lon, lat]`, and that z runs from −705.5 m to +1,809.4 m over a footprint whose real ground is roughly 0–1,500 m. It is neither a burial depth nor a ground height: it is dropped and the stroke is clamped. Feeding those 3-tuples to a flat lon/lat reader does not throw — it silently mis-plots the network — so arity is checked per vertex. The same file also holds one `geo_shape: null` row (which still carries a `geo_point_2d`) and eight `MultiLineString` rows in a dataset that is otherwise all `LineString`.
- **The power-station file is seven annual editions stacked in one table.** Its 98 rows are 14 sites × `annee_de_reference` 2019…2025: summing the power column gives 50,372 MW for a fleet that is **7,196 MW**, and plotting the rows stacks seven dots on each of 14 coordinates. Only the newest edition of each site is drawn. The editions also disagree — Landivisiau is `En projet` in 2019 and 2020, `En service` from 2021, and publishes a commissioning date only from 2022 — and no endpoint promises an order (the export answers 2025 first, the records API answered 2023, 2022, 2025, 2021, 2024, 2019, 2020 for that station), so "the first row per site" is a coin flip. The card names the edition read and the status the older ones claimed. It is **installed capacity, never live output**: what those machines are producing right now is the Mix élec layer's `gaz` filière, which RTE does not break down per station without an API account.
- **`site_ouvert` is the string `"False"`, and `Boolean("False")` is `true`.** Three of the 854 injection sites in a file titled *en service* are closed, each with a closure date and its capacity zeroed; they are counted and never drawn. One further site publishes no coordinates and is counted, not drawn. 850 remain.
- **Most injection points feed a network this layer does not draw.** 741 of the 850 inject into the local *distribution* network (GRDF and the ELDs), 109 into the transmission network whose trace is on screen. Both are drawn, at different opacities, and counted as two separate legend rows — and no connector is ever drawn between a site and a pipe, because none of these files publishes that link.
- **The catalogue's own `modified` date is wrong, so it is not used.** ODRÉ reports `modified: 2019-11-30` for a power-station file that carries a 2025 edition. Licence Ouverte 2.0 obliges publishing the data's update date, so the layer reports the edition year the projection actually read.
- **The two networks are two companies' pipes and are never merged.** Their bounding boxes overlap — 58 NaTran rows sit inside Teréga's box — but a shared box is not a shared asset. Two colours, two legend rows, two length figures (31,420 km and 4,686 km), and a stroke of one is never chained onto a stroke of the other.
- **French EV charge points (IRVE).** Keyless. The *fichier consolidé des bornes de recharge pour véhicules électriques* is assembled daily by transport.data.gouv.fr from the operators' own IRVE filings and republished on ODRÉ under Licence Ouverte 2.0. Measured 2026-08-27: **231 079 points de charge**, one row per charge point. `/api/irve-fr/sites` answers one box no wider than 0.35° using Opendatasoft's own `group_by`, which is what makes the layer affordable — the 4 017 charge points in central Paris come back as 469 grouped rows (300 KB, 0.77 s) instead of 3.2 MB of flat export, and fold again to **188 sites** in a 105 KB answer. The densest legal box (Paris, 0.34°) is 22 145 charge points → 2 227 sites, 1.26 MB, 0.70 s cold. Cached 6 hours in memory and on disk under `.gev-cache/irve/`, because the consolidation itself only runs once a day.
- **Three regimes, because 39 579 sites is not a national picture.** The layer answers at the scale it is being asked at. With the whole country in view (latitude span ≥ 9.5°, ~1 400 km up) it paints the 96 **départements**; once France is cropped it draws the **maillage** — real site positions, thinned; below ~25 km, where the 0.35° viewport query becomes answerable, it draws **every site** with its operators and connectors. Only one is ever on screen, and each has its own legend, so a colour cannot be read against the wrong scale. Latitude rather than the larger span decides, because on a 16:10 viewport longitude runs ~2.4× wider (measured: 9.53° lat against 24.42° lon at 1 400 km) and would keep the choropleth up long after France had been cropped top and bottom.
- **The maillage is thinned spatially, never by rank.** `/api/irve-fr/mesh` serves the whole national point set once — 39 579 tuples, 0.9 MB, cached a day — and the client picks per viewport, so panning costs no round trip. The pick buckets the view into a 30 × 20 grid and gives every occupied cell a dot before any cell gets a second, then spends the rest (1 100–2 200 by zoom) walking position order at a fixed stride. Taking the biggest N instead would collapse France to a dozen bright conurbations and erase the Massif Central, whose sparseness is a real finding.
- **The cell's representative is its most common band, not its biggest site.** Measured over France at 900 km, picking the largest drew **46.2% of the dots as high-power DC when 12.2% of the sites in view were** — the biggest site in a rural cell is almost always the motorway HPC bank, so the map said France runs on 300 kW chargers when it runs on 22 kW ones. Representing each cell by the largest example of its *modal* band brings that to 8.7% against 12.2% true, and 12.7% against 14.8% at région scale. A residual bias survives and is stated rather than hidden: `normale` comes out ~46% against 36% true, because the commonest band wins the most cells — an error toward the typical rather than the rare, and the legend says the mix shown is a sample.
- **This is INSTALLED CAPACITY, not availability.** Nothing in these 231 079 rows says whether a charge point is free, working, or occupied — that lives in each operator's own OCPI endpoint, behind a contract. The layer therefore never draws an availability colour and never prints a "libre" count. It colours a site by the highest power band installed there and sizes it by how many charge points are there.
- **The published geometry is unusable, twice over.** `geo_point_borne` is null on **all 231 079 rows**, so Opendatasoft's `within_bbox()` matches nothing at all and the viewport filter has to be a numeric predicate on the consolidated columns. Worse, `coordonneesxy` is **labelled backwards** — its `lon` key holds the latitude — on every row checked (32 091/32 091 across Île-de-France), which puts Gennevilliers off the coast of Somalia. Only `consolidated_latitude` / `consolidated_longitude` are read.
- **The station id fragments the station, so the site is the coordinate.** Q-Park's Grande Arche car park at La Défense publishes **127 distinct `id_station_itinerance` at one coordinate**, one per charge point; Interparking Clichy-Montmartre publishes 82; and 1 192 rows nationally publish the literal string `"Non concerné"`, spread across coordinates up to 55 km apart. Charge points are therefore grouped by coordinate rounded to ~1.1 m — which also merges the same Brétigny-sur-Orge site published at six decimals by one feed and seven by another. `nbre_pdc`, the operator's own declared count, is not used: only 2 641 of 6 272 Île-de-France stations have it agreeing with the rows actually published (Bump's Lobau station declares 203 and publishes 229; one Citeo station declares 10 and publishes 1).
- **The same charge points are published twice, and both figures are reported.** Measured over Île-de-France: **442 of 3 812 sites (11.6%) carry two or more "operators" publishing an identical power profile at the same point** — TotalEnergies Charging Services beside TotalEnergies Marketing France (378 sites), SPIE CITYNETWORKS beside SPIE CityNetworks (107, pure case), ENGIE Vianeo beside its Greenflux back end (35) — worth 2 392 charge points, 7.5% of the area's total, that a naive sum counts twice. Identical profiles collapse to one; merely overlapping ones never do (only 3 of 576 clusters were a single charge point, so the test is precise rather than lucky). The card names what was collapsed and the panel reports both totals.
- **Kilowatts that are watts are counted, never rescaled.** `puissance_nominale` is kW per the IRVE schema, and 6 981 rows nationally (3.0%) fall outside any envelope a charge point can occupy: 5 315 publish ≤ 0 kW and 1 666 publish more than 400 kW — headed by 771 rows at exactly 7 360 and 90 at 3 680, which are 7.36 kW and 3.68 kW in watts. Dividing by a thousand is a guess that happens to be right there and turns a genuine 600 kW bank into 0.6 kW elsewhere, so those charge points go to an explicit *puissance non exploitable* band in neutral slate — counted, named, and never given a rung on the power ramp — while the card still prints the published figure verbatim.
- **"Not verified" is not "wrong".** `consolidated_is_lon_lat_correct` is False on 37% of the file, and reading that as a bad coordinate would discard a third of France. It is False in two different situations, separable because the consolidation fills `consolidated_commune` only when it verified the INSEE code: **False with no commune** (80 545 rows) means the pipeline could not *check* the position, and those are kept and flagged on the card; **False with a commune** (5 361 rows) means the position contradicts a commune the pipeline *did* verify, and those are withheld and counted — QOVOLTIS publishes "Route du Baganais", verified commune Le Porge (Gironde), at −44.996 / +44.996, south of Madagascar. 24 rows at exactly (0, 0) are dropped outright.
- **Eight spellings of a boolean, and mojibake in a closed vocabulary.** `gratuit`, the five `prise_type_*` columns and `station_deux_roues` arrive as `"True"`, `"true"`, `"TRUE"`, `"False"`, `"false"`, `"FALSE"`, `"1"`, `"0"` and null — all nine forms measured in one pull — and `Boolean("False")` is `true` in JavaScript, which would report every paid site as free and fit every socket with a CCS plug. Separately, some publishers ship accents decoded through the wrong table (`"Acc\x8fs libre"`, 48 Île-de-France rows, plus rarer `"Accčs libre"` and `"Acc¸s libre"`), which would split one legend row into four. The C1 block is re-read through Mac Roman — an exact, reversible repair — and the three enumerated columns are then matched to the IRVE schema's own vocabulary on their ASCII skeleton. A value matching nothing passes through as published.
- **Freshness is per site, not per poll.** `date_maj` across Île-de-France runs from 2020-11-10 to 2026-07-31 with a 10th percentile of 2023-07-06 — a tenth of the file has not been touched in three years. The card prints the span of the site's own declarations, never the age of the request.
- **French doctors, and the register that has no coordinates.** Keyless. The CNAM publishes the *Annuaire santé Ameli* under article L. 1461-2 of the Code de la santé publique — 555 249 rows weekly, of which 194 114 are doctors — and its address block is named `coordonnees_*` in the sense of *contact details*: **there is not one latitude in the 155 MB**. Every ready-geocoded copy in circulation descends from the PREVIOUS CNAM directory, deprecated in December 2025, and still says *"contrat d'accès aux soins"* — a device closed to new signatures on 2016-12-31. The one daily-geocoded national register, Atlasanté's RPPS layer, answers HTTP 403 outside the ARS network. So `scripts/build-medecins-fr.mjs` geocodes the register against the BAN in three passes and ships the result: **64 232 of 64 625 addresses placed, 99.4 %**, 82.7 % at the exact door and 1.1 % at a commune centre that says so on its card.
- **The register has no identifier, so the layer counts names and says which.** No RPPS, no ADELI, no SIRET. "How many doctors" is therefore unanswerable from it: the file publishes **187 584 (name, address) tuples and 117 922 distinct names**, and the layer's `getStats()` reports `medecins` and `entrees` separately so neither can impersonate the other. Checked against the CNAM's OWN headcount of the same population (`demographie-exercices-liberaux`, millésime 2024, 112 159): **+5.1 % nationally**, 23 professions between −1.5 % and +15.1 %, and per DÉPARTEMENT a median gap of **+2.1 % with 97 of 101 inside [−10 %, +15 %]** — so the geocoding moved nobody between departments. `npm run medecins:registry -- --verifier` replays it.
- **Three traps the build neutralises, each measured.** (i) A radiologist is listed at every imaging site they cover — **5.53 entries per name against 1.18 for a GP** — so dot size is the distinct-name count and never the entry sum. (ii) `01`, `22` and `23` all read `Médecin généraliste` with nothing published to tell them apart; grouping by code loses **7 585 GPs, 11 % of them**, so codes are folded onto labels and the fold is published in `specialitesAlias`. (iii) **9 328 doctors practise in more than one département**; counting distinct names per département and adding the columns answers 130 330 for a country holding 117 922, so `departements[dep][0]` assigns each doctor to one département and the column sums exactly to the national figure.
- **The national regime paints ACCESSIBILITY, not a count, and that is a measured choice.** The median French person lives **0.7 km from a general practitioner** and only 0.49 % of the population is beyond 10 km, so a choropleth of counts would say "France is covered" and be useless. What is scarce is capacity. The layer therefore paints the DREES's APL — *how many consultations a resident can reach in a year*, neighbours included, weighted by each doctor's real activity, travel time and the local age structure. The headline series is **general practitioners aged 65 or under**, which is what the DREES publishes and quotes (3,3 for 2024); reading the all-ages column instead answers 3,72 and disagrees with every published figure. The build reproduces the DREES's own published decile table across three millésimes — mean, first decile, tenth decile — to ±0.02.
- **The APL also carries the retirement cliff, and the cards say it.** The same indicator is recomputed while retiring everyone over 65, 62 and 60. Nationally that reads **3.73 → 3.27 → 2.91**, so France loses 22 % of its general-practice access to the over-62s alone; the Yonne would lose 35 %. That is the closest thing anyone publishes to "and in five years".
- **What the layer costs on the wire, measured.** A full session — national view, mesh, a city, then thirty micro-moves — transfers **593 kio**, against 3 360 kio before the proxy was tuned. Four changes got it there: every route is **gzipped** (Vite compresses its module graph and nothing else, so these went out raw), the two invariant payloads are serialised and compressed **once**; the **practitioner names left `/sites`**, where on a dense Paris box they were 40 % of 1 451 kio — 16 069 names shipped to draw 5 907 dots of which a reader opens one — and are now fetched per address on the click that wants them; a **view already served costs nothing**, because `moveEnd` and `changed` fire on the same gesture with rectangles differing in the twelfth decimal, and a superseded request is aborted rather than left to arrive; and the site scan runs through a **0.25° grid** so it is bounded by the viewport, not by the size of France. The two shipped artifacts are gzipped in the repository — **3.67 MB against 16.18 MB** — for 15 ms of `gunzipSync` once per process.
- **What no public file answers, and the layer refuses to imply.** Whether a doctor takes new patients, and how long the wait is, are the two questions people most want answered, and neither is in the register. The layer says who is listed at an address and what they charge — **94 % of GP entries are secteur 1 against 18 % of ophthalmologists, 63 % of whom set their own fees** — and stops there.
- **French schools (Annuaire de l'éducation).** Keyless. The MENJ publishes its own register on data.education.gouv.fr under Licence Ouverte 2.0 and rebuilds it daily. Measured 2026-09-01: **68 939 rows**, one per UAI (*unité administrative immatriculée*), of which **68 557** are `etat = OUVERT` and **68 158** are both open and carry a coordinate — the set the layer draws. `/api/schools-fr/sites` answers one box no wider than 0.35° through the portal's `exports/json` endpoint rather than `records`, because Explore v2.1 caps a `records` page at 100 rows and the densest real box (Paris at 0.35° — **5 506 establishments, 3.26 MB, 0.57 s**) would otherwise be 56 round trips. `/api/schools-fr/departements` and `/mesh` are built by ONE national export (8.5 MB, 2.4 MB gzipped) and cached together for 24 hours under `.gev-cache/schools-fr/`; the mesh reaches the browser as 68 158 tuples, **1.66 MB, 0.63 MB gzipped**.
- **The register has no roll, so the roll is a join — and the join is 91.7% complete.** Nothing in the annuaire says how many pupils are in a school. Dot size comes from the ministry's four per-level *effectifs* datasets at rentrée 2025 (`fr-en-ecoles-effectifs-nb_classes`, `…college-effectifs-niveau-sexe-lv`, `…lycee_gt-…`, `…lycee_pro-…`), joined on the UAI: **57 683 of the 62 918 open, geolocated teaching establishments get a roll**, 11 237 267 pupils in total. The 5 235 that do not are named rather than averaged away — **2 212 are sub-UAI SECTIONS** (1 462 SEGPA, 750 SEP) whose pupils are already counted inside the collège or lycée at the same coordinate, and 455 are under the ministry of Agriculture, which publishes its rolls elsewhere. A school with no roll is drawn at the base size and its card says *effectif non publié*; it is never drawn as, or described as, a school with no pupils.
- **A UAI is not a building, and the layer says so.** Several UAIs routinely share one physical site, so two dots at one address are the register's administrative unit showing through rather than a duplicate. Every site carries `etablissement_mere` when it has one, and the card names the parent.
- **The coordinate carries a published quality, and it is surfaced.** `precision_localisation` is the register's own account of its geocoding: 50 874 rows at `Numéro de rue`, 10 139 at `Rue`, 3 600 `PLAQUE_ADRESSE`, and **2 159 at `Ville` — the commune centroid, not the school** — plus a long tail of 18 further spellings from the académies' various pipelines. They fold onto a four-step ladder, an unrecognised spelling resolves to *inconnue* rather than inheriting "exact address", and a site geocoded only to its commune says so on its card.
- **399 open establishments have no coordinate at all, and 332 of them are one region.** Measured: `position IS NULL` on 399 rows, every one of them `OUVERT`. **French Polynesia's 311 establishments and Wallis-et-Futuna's 21 are ungeocoded in their entirety** — not a sample, all of them — plus 49 in New Caledonia; only 18 are metropolitan. They are excluded at the query rather than placed at a commune centroid, because an invented coordinate is indistinguishable from a real one once it is a dot.
- **The choropleth is metropolitan, and admits it.** The bundled département polygons are 96 features with no overseas geometry, so **2 762 open, geolocated schools fall outside every polygon** — La Réunion 855, Guadeloupe 448, Martinique 403, Nouvelle-Calédonie 334, Mayotte 333, Guyane 319, and 9 metropolitan island schools (Belle-Île, Ouessant, Sein, Bréhat) that the simplified outlines drop. They are counted, named by their published `code_departement`, and reported on the national card; the other two regimes draw positions rather than polygons and show all of them. Assignment is point-in-polygon and never a code join: the register zero-pads to three characters and spells Corsica `02A`/`02B` where the IGN outlines use `28`, `2A`, so a code join would miss every row silently.
- **The booleans are 1 / 0 / null, and null is not false.** `restauration`, `hebergement`, `ulis`, `segpa` and `apprentissage` publish all three states, where null means "not declared". A plain coercion turns every undeclared school into one with no canteen, so they are read to `true`/`false`/`null` and the card lists what is declared present rather than denying what was never stated.
- **IPS is an ATTRIBUTE of a school, not a layer — and it reaches two schools in three.** Keyless, Licence Ouverte 2.0, same portal as the Annuaire. The DEPP's *indice de position sociale* publishes no coordinate at all: every one of its 43 322 rows is keyed on the UAI, so a layer would have to borrow its geometry from `schools-fr`, which is another way of saying it IS `schools-fr`. It is joined exactly as the four *effectifs* files are, and it moves neither map channel — colour still means level, size still means roll. Measured 2026-09-02 against the live files and the live register: `schools-fr` draws 68 158 open geolocated rows over **68 083 distinct UAI**, of which **62 857 can carry an index** (Ecole 48 169 · Collège 9 055 · Lycée 5 547 · EREA 79, plus 7 the register leaves untyped and the DEPP indexes anyway). **42 974 find an IPS row (68.4%)** and **40 529 come back with a number (64.5%)**. Per type: Ecole 66.9% joined / 61.8% valued, Collège 77.8% / 77.7%, Lycée 65.4% / 65.4%, EREA 97.5% / 97.5%. A school with no published index is drawn exactly as before and its card says *IPS non publié pour cet UAI* — it is never coloured, never sized and never read as average.
- **Four datasets, four DIFFERENT newest rentrées, and a single `max()` drops three quarters of the join.** Read from each dataset's own `group_by=rentree_scolaire`: `fr-en-ips-ecoles-ap2022` stops at **2024-2025 (32 494 rows)** where `fr-en-ips-colleges-ap2023` (7 089), `fr-en-ips-lycees-ap2023` (3 662) and `fr-en-ips-erea-ap2022` (77) all reach **2025-2026**. A global newest-rentrée returns 2025-2026 and silently drops every école. Each dataset therefore discovers its own year, floored at what the module was measured against, compared as a `YYYY-YYYY` STRING behind a format guard — `Number('2024-2025')` is NaN, so a numeric max would return the floor for ever. The files are also cumulative (97 080 école rows are three school years stacked), so the rentrée is pinned in the `where` or every school appears three times with three different indices.
- **Lycées have no `ips` column, and their establishment figure blends two populations the file publishes apart.** Écoles publish `ips`; collèges and EREA publish `ips` + `ecart_type_de_l_ips`; lycées publish `ips_voie_gt`, `ips_voie_pro`, `ips_post_bac` and `ips_etab` with `type_de_lycee` ∈ {LEGT 1 565, LP 1 097, LPO 1 000}. A join written against `ips` drops all 3 662. `ips_etab` is the figure carried — the only column defined on 3 661 of 3 662 and the only one comparable across the three types — but the card names it as an establishment figure and then names the voies underneath it, because over the **931 LPO that carry both, the median GT-to-pro gap is 18.1 IPS points, the 90th percentile 27.9, and the widest is 0312746S at GT 140.1 against pro 92.4** — 47.7 points inside one `ips_etab` of 126.3. It is not a copy of a single voie either: 2 042 rows carry `ips_post_bac`, which is folded into `ips_etab` and nothing else (0020031Y publishes GT 97.4 and `ips_etab` 95.4).
- **`fr-en-ips-erea-ap2022` misspells its own column, and it is an HTTP 400 rather than a null.** It names the establishment `nom_de_l_etablissment`, no second 'e'. Verified both directions against the live endpoint 2026-09-02: the correct spelling returns `ODSQL query is malformed: Unknown field: nom_de_l_etablissement. Clause(s) containing the error(s): select.` on the EREA dataset, and the misspelling returns the same on the écoles one. The `select` is built per dataset from the spec's own field name and is never shared, so nobody discovers this in production.
- **The reference values are per-type for lycées, and picking the wrong column is a wrong number.** Écoles, collèges and EREA publish `ips_national` / `ips_academique` / `ips_departemental`. Lycées publish them split three ways, and nationally at rentrée 2025-2026 that is **LEGT 120.2, LPO 104.4, LP 89.9** — 30 points end to end. The card carries the départemental and national anchors for the school's own type, and the écart against the département. Two things send that écart to the national anchor instead and both are measured: the départemental reference is missing (2 LEGT rows, 10 LPO, 3 LP), or it EQUALS the school's own index and therefore contains it and little else — **184 rows, including 49 of the 77 EREA**, because there is at most one EREA per département. With neither published (94 collège rows and 39 lycée rows carry no `ips_national`) the card prints the anchors it has and no écart. The académie and the `_prive`/`_public` splits are deliberately not fetched: three territories on a card make none of them the answer, and comparing a private school only to private schools grades the gap on a curve.
- **`NS` is a published value, and `Number('NS')` is NaN.** The écoles file writes the literal string `"NS"` — *non significatif*, the DEPP's secrecy marker for a school too small to publish — in **2 504 of its 32 494 rows (7.7%)**. `Number(row.ips) || 0` turns every one of them into an IPS of **0** on a scale whose measured range is 54.9 to 162.7. They are read as a sentinel and the card says *IPS non significatif (« NS ») — effectif trop faible…*, which is a different fact from a school the DEPP never examined. Two more blanks are real and counted apart: 2 collège rows publish `ips = null` (9750025D Saint-Pierre-et-Miquelon, 0133827P) and 1 lycée row publishes every IPS column null (0754089M, Paris 11e). In total **2 445 schools this map draws are inside the DEPP's files and still have no index.**

It is a different quantity from the index it disperses and cannot borrow its bounds. Écoles publish no dispersion at all; the other three always do, and it rides the card's headline as `(écart-type 34,3)`.
- **Three types for one measure, on one portal.** `ips` is TEXT in the écoles file (`"119.5"`, and `"72"` for an integer), DOUBLE in the collèges and EREA files (96.3), and every lycée column is TEXT again. Same publisher, same portal, same measure, one reader.
- **Coming the other way, 348 indexed establishments are not on this map.** The index holds 43 322 UAI and 42 974 of them are a school `schools-fr` draws. The rest are closed in the Annuaire, uncoordinated, or absent from the open register: **1300023U is the Lycée Comte de Foix in Andorra la Vella**, and 9830313Y and 9830298G are New Caledonian — the territory the layer already documents as partly uncoordinated. The national rollup carries the count and five named examples so the claim is checkable.
- **What it costs, and where it deliberately costs nothing.** Eight requests once per server process — four `group_by` discoveries and four exports — **7 598 242 bytes raw / 750 413 gzipped, 3.4 s cold and 0.64 s warm**; the four full-column exports would be 33 040 379 / 1 587 950, so the per-dataset `select` lists take 77% off. On the client, the densest legal viewport (0.34° over Paris, 4 725 establishments) goes from 2 794 171 raw / 349 436 gzipped to **3 267 807 / 380 177 — +17.0% raw and +8.8% on the wire**. The **maillage carries no IPS at all**: that pack ships coordinates without names to stay at 1.66 MB against 5.42 MB, and an index per tuple would put it straight back, so the index rides the per-click register lookup the name already pays for. Losing the DEPP files does not break the layer — it draws exactly what it drew before and every affected card says *Indice de position sociale indisponible — fichier DEPP injoignable*, which is not the same claim as "not published"; a single failing file costs only that level its index.
- **French higher education (Effectifs d'étudiants inscrits + Cartographie Parcoursup).** Keyless. One dot per establishment would put 80,000 students on a street corner; one dot per row would draw the same campus seven times, once per degree level. - **French childcare (Cnaf coverage rate).** Keyless. **There is no national open register of crèches, and that was measured before this layer was built rather than assumed.** The Cnaf — which holds the list behind monenfant.fr — publishes 210 open datasets and not one is an establishment: all are aggregates by IRIS, QPV, commune, EPCI, département and national. - **The choropleth is metropolitan, and that omission is the finding.** The bundled polygons are 96 features, so **6 of the Cnaf's 102 rows cannot be painted**: Guyane 13,4, Saint-Martin 30,2, La Réunion 38,5, Guadeloupe 44,1, Saint-Barthélemy 47,5, Martinique 55,2. **Every one is below the national rate and Guyane sits at 22% of it — the lowest coverage in France by a factor of three.** Meanwhile not one metropolitan département reaches the lowest band: measured over the 96 painted, that bucket is EMPTY. A map that stopped at the coastline would not merely omit six rows, it would delete the entire bottom of the distribution. They are returned with their rates intact and named on the national card. The join is by CODE and not point-in-polygon — verified 2026-09-01, the Cnaf's `01`–`95`/`2A`/`2B` spellings match the IGN outlines character for character, which is the opposite of the Annuaire de l'éducation next door (it zero-pads to `045` and would miss every row).
- **Some rows are not areas, and they are not spelled alike.** The EPCI rate file carries `numepci = "XX"` — a placeholder for communes belonging to no intercommunalité — and it holds a REAL, extreme value (195,8), which makes it the single most damaging row in the layer: left in it is the national maximum, it anchors any ramp, and it is drawn nowhere. The département PLACES file spells the same idea `XXX`. The test matches any run of X rather than a literal, which is the difference between catching one and catching both. With `XX` gone the real EPCI range is **2,7** (CC de l'Est Guyanais) to **160,5** (CC Altitude 800), median 62,9, four EPCI above 100.
- **A rate above 100 is a fact and is never clamped.** It counts PLACES per 100 resident children under three, so a commuter town or a small mountain denominator legitimately passes it. Four EPCI do. Clamping would turn a real finding into a ceiling.
- **The commune scale is a city detail, not a national mesh.** The Cnaf publishes it only for communes over 10 000 inhabitants — **1 061 of ~34 875** — so a commune choropleth would be 97% holes. It is drawn as points below a city-scale zoom, alongside the EPCI point that always exists, and every commune card says so. It also breaks Paris, Lyon and Marseille down by *arrondissement municipal*, which `geo.api.gouv.fr/communes` omits by default: without the extra `type=arrondissement-municipal` call the scale loses 45 rows, all of them in the three largest cities in France.
- **`annee` is an int in six files and a DATE in the seventh.** `txcouv_pe_nat` types it as a date where every other file uses an int, so one `where=annee=2023` clause cannot serve both — the national file answers HTTP 400. It is two rows, so it is read whole and filtered in code.
- **The published components do not sum exactly.** Every rate is rounded to 0,1, so the five leaves add to the global only within rounding. The global figure is the published one and is never recomputed from the parts. The two subtotals the Cnaf also publishes (`eaje`, `ind`) are sums of the leaves and are deliberately kept off the card, so the same children never appear twice to a reader adding the column up.
- **Points, not polygons, below the national view — and the cost of fixing that is measured.** A rate belongs in an area fill, so EPCI polygons would be the honest rendering. `geo.api.gouv.fr` refuses an unfiltered contour request, so the pack would be 1 255 separate calls, **66 MB and 3,1 million vertices** before simplification, landing as a new ~1,5 MB bundled asset whose vintage drifts from the data's every January. Until that exists the layer puts the number at the area's centre and says so on every card, rather than inventing a boundary. Measured today: 1 250 of the Cnaf's 1 251 EPCI codes match the current découpage (99,92%), the one miss being the `XX` placeholder.
- **The layer answers a BLOCK below 1 500 m and a POINT above it, and the split is measured.** "Could the car park opposite become twenty-five metres of construction?" is a question about the plot OPPOSITE, which a point query cannot answer. `zone-urba` is therefore asked for over a box around the camera's ground point — clipped to the view, so nothing off screen is fetched, and capped at **0.02°** for the same reason the cadastre layer settled there: at twice that side Paris answers 243 zones and 1.2 MB against 52 zones and 405 KB. The gate is camera ALTITUDE, not the span of the view rectangle, which on a tilted camera reaches the horizon. Above the gate the point regime is unchanged and still correct.
- **The easement half is ALWAYS a point, and one measurement decides it.** A 390 m box over Lyon's Presqu'île returns **210 easement features and 2.3 MB**. Measured at the zoning ceiling on 2026-09-01, upstream / on the wire / entities drawn: Lyon point 725 KB / 409 KB / 153, full box **4 004 KB / 1 823 KB / 1 182**, hybrid 888 KB / 506 KB / 218. Four times the payload for the half of the answer a point already gets right — "what reaches this address" is the correct question for an easement.
- **It costs bytes, not frames.** Measured in the browser on the shipped build over IGN ortho, both regimes: median frame **0.6–1.4 ms**, worst frame after a redraw **1.4–2.2 ms**, **zero frames over 16 ms** in either. Ground fills batch by material and there are eight zone colours. Upstream the box costs +13% to +27% in a city and 17× in a rural commune, where the point answer was 30 KB — 509 KB and 170 KB on the wire in absolute terms.
- **`zone-urba` truncates at 5 000 features, HTTP 200, and says so only in `totalFeatures`.** Measured 2026-09-01: a 0.15° Paris box returns 4 105 of 4 105 whole; a 0.40° box **5 000 of 17 182**; a 1.0° Île-de-France box **5 000 of 46 500**. Unlike the cadastre, zoning has no legitimate gaps, so a truncated answer reads as a commune with mixed zoning rather than as a broken feed. A box over the ceiling is refused whole and the true count is printed. At the layer's own 0.02° ceiling the densest measured box answers 55 zones.
- **`atPoint` is decided by whoever was asked, and the drawn shape never decides it.** Under a point query every returned feature intersects that point by construction — APIcarto has answered, and re-deciding can only disagree. Under a box query the layer decides, against the ring as PUBLISHED. That distinction is not academic: Ustaritz's `UB` outer ring is 521 vertices decimated to 400 for drawing, and the coordinate APIcarto itself answers `UB` for falls **outside the decimated ring** — wrong by exactly the tolerance the layer already declares. A simplification must never decide which rule applies to a house.
- **Each zone carries its code on the ground, anchored on the longest interior chord rather than the centroid.** A block of fifty coloured polygons is a colour chart otherwise: the family is legible from the hue, but `UB` against `UYc` — both orange, one residential and one industrial — is not. The centroid of a PLU zone routinely lands outside it, because a zone is often a meander along a village street or a ring around a hamlet, and a label on ground its own colour does not cover is a worse lie than no label. Verified on all 55 zones of a real answer: every anchor inside its own drawn shape. A zone narrower than ~33 m of longitude is drawn and coloured but unlabelled.

- **A PLU zone is drawn as a WASH, and the enclaves are cut out of it.** The layer drew bare outlines until an operator asked how one house could be in two PLU zones at once. Two answers, and both are here. **Ours:** `projectGeometry` kept outer rings only, on the reasoning that a hole in an outline is invisible — true, and irrelevant once the shape is filled. Measured at Ustaritz (64547) on 2026-09-01, the answer for one point in the village centre is zone `UB`, ONE polygon, **two interior rings**: 6 646 m² the same PLU zones `UE` (the school) and 50 686 m² it zones `UYc` (the industrial estate). Filled without them, UB paints 57 332 m² of ground with a rule that does not reach it; across the commune that is 14 interior rings and 299 441 m². Rings are now carried, spent out of the vertex budget WITH their outer ring so a hole can never be the thing a budget drops, and stroked — an enclave has a boundary too, and it is the line that says the rule stops here.
- **The register's own answer: two communes can zone the same ground, and it is measured.** Sampled on a 35 m grid over a 9 × 6 km box around Ustaritz — 34 126 points, **17 of them (0,05%) fall inside two zoning polygons at once, every one at a commune limit**. Seven urbanism documents overlap in that box across **73 polygon pairs and 5,3 ha**, headed by 24 024 m² where Cambo-les-Bains and Halsou both zone `Nbd`, and including 525 m² that Jatxou zones `UD` (urbaine) and Halsou zones `A` (agricole). Each commune digitises its own PLU against its own idea of where the limit runs and the Géoportail stacks the documents without reconciling them. The layer reports `zoneCount` so more than one zone under one point reads as the register disagreeing with itself rather than as a broken answer.
- **`typezone` is SEVEN values, not four, and the four-value table greyed out the one family the layer exists for.** Measured 2026-09-01 across twelve APIcarto boxes — Paris, Lyon, Lille, Toulouse, Marseille, Rennes, five peri-urban boxes around Nantes, Orléans, Annecy, Caen and Perpignan, plus Ustaritz — **4 216 zoning features, and plain `AU` appears ZERO times**. Every à-urbaniser zone published `AUc` (97) or `AUs` (23), 2,85% of the sample, all of it falling to the unknown-value grey at the unknown-value weight. And the `c`/`s` is the most decision-changing bit in the layer: **`AUc` is open** — the plot opposite can be built under the PLU as it stands — while **`AUs` is closed until the document is modified or revised**, which is what the register itself calls "à urbaniser bloquée", "réservée à l'extension future de la ville", "à urbaniser dans un 2e temps". Same magenta family, cooled and quieter. `Ah`/`Nh`, the built pockets inside the agricultural and natural zones, take their family's hue brightened.
- **The wash weights are measured, not chosen.** The same polygon was repainted at five alphas over Ustaritz on IGN ortho, under this app's own colour grading and scope mask, and each frame differenced against the unpainted one across the ~380 000 pixels the zone covers: **0.18 moved the picture by a mean of 3/255 in red and could not be seen at all**; 0.22 by 5, 0.28 by 11, 0.33 by 17, 0.40 by 24. The app attenuates a nominal alpha by roughly a factor of four, which is why the intuitive "0.18 is plenty" was wrong. Shipped: `AUc` 0.42, the `AUs`/`Ah`/`Nh` exceptions 0.34, `U` 0.30, and `A`/`N` 0.22 — they are most of the country, and at the urban weight a natural zone washes a whole valley teal.
- **Servitudes stay lines, and the lines are DASHED.** They are not zoning and a solid stroke would say they were; they are also the wrong size to fill, since one measured `pm1` technological-risk envelope is 759 polygons spanning kilometres and a wash of it tints the view rather than a plot.

- **French cadastral parcels (PCI vecteur).** Keyless. IGN's Api Carto serves the DGFiP's Plan Cadastral Informatisé as GeoJSON with no key and no account, reflecting the `Origin` header. `/api/cadastre-fr/parcelles` answers one box no wider than 0.02° — the client gates on camera ALTITUDE (≤ 1 500 m) and asks for a box anchored on the point the screen centre meets the ground, clipped to the view, because `computeViewRectangle` on a tilted camera reaches the horizon and describes the pitch more than the zoom — with TWO parallel upstream calls — `parcelle` for the map and `feuille` for the scale each of those parcels was drawn at — and folds them to one document: measured 2026-09-01, central Paris returns 533 parcels in 353 KB of GeoJSON and leaves as 268 KB. Cached 24 hours in memory and on disk under `.gev-cache/cadastre/`, because the PCI is republished monthly. The proxy exists despite the open CORS because Api Carto answers `Cache-Control: private, no-cache, no-store, must-revalidate` — the browser cache is forbidden from helping, so every pan would otherwise be a fresh round trip to a free public service for data that changes once a month.
- **This is a FISCAL document and the card says so.** The cadastre exists to assess property tax; in France a property limit is fixed by BORNAGE — a géomètre-expert's survey under article 646 of the Code civil — and the cadastral plan has no legal force over it. A crisp polygon on a photorealistic globe is exactly the thing a reader takes for a surveyed limit, so every card ends on that line, before anything else can be misread.
- **The tolerance of a cadastral line is published, and it varies twentyfold.** Each parcel belongs to a `feuille`, and the feuille publishes the `echelle` of the plan it was drawn on. Measured across 673 sheets in nine boxes on 2026-09-01: **1:250** (114 sheets, central Strasbourg), 1:500 (345), 1:1000 (154), 1:2000 (48), 1:2500 (4), 1:4000 (5) and **1:5000** (3, the Landes forest) — zero nulls. At the conventional 0,5 mm of drawn line that is **±0,13 m to ±2,5 m** for the same word "boundary". The layer colours every parcel by that band and prints the figure with its assumption attached, because a bare "±0,25 m" reads as a survey result.
- **A sheet is not identified by (commune, section, feuille).** Lyon publishes section `AL` feuille 1 in FIVE arrondissements — 381, 382, 383, 385, 386 — and the 5e's copy is drawn at 1:1000 while the others are at 1:500. Joining without `code_arr` gives those parcels a coin-flipped tolerance. With `code_arr` in the key there were **0 collisions across 27 595 parcels and 450 sheets**; without it, 2 in Lyon alone. The join is five parts wide.
- **`idu` does not start with `code_insee` for 38% of urban France.** The identifier's first five characters are the ARRONDISSEMENT code: a Marais parcel is `75103000AP0045` while its `code_insee` is `75056`. Measured over the same 27 595 parcels: **10 588 mismatches**, every one in Paris, Lyon or Marseille. Reassembling an IDU from `code_insee` produces a key that joins to nothing in DVF for the three cities where property data matters most — and `code_insee` + section + numero is not unique either (it matches 11 different parcels in Paris). The published `idu` is carried verbatim and never rebuilt.
- **Api Carto caps every request at 5 000 features and says so only in `totalFeatures`.** `_limit=4999` returns 4 999; `_limit=5000`, `5001` and `10000` all return exactly 5 000, HTTP 200, no warning (Paris, 0.034° box, 12 483 parcels in it). Worse than a wrong count: paging with `_start` walks an internal order that mixes arrondissements, so a truncated answer is a cadastre with SCATTERED holes — which is precisely what a complete one looks like over the public domain. A box over the cap is therefore **refused whole**: nothing is drawn and the true count is printed. That refusal is the exception, not the experience: at the layer's 0.02° ceiling on a 16:10 viewport the densest French cities answer 2 100–2 400 parcels.
- **The holes are the streets, and the row says how many.** The cadastre parcels private land and the public property that has been given a parcel; roads, squares and rivers have none. With parcels clipped to the view (they arrive INTERSECTING it, which is why the first version of this number reported 141% over La Défense), measured 2026-09-01: **45,7 % of Lyon's Presqu'île** is cadastred, 32,7 % around the Champ-de-Mars, 80,9 % in the Marais, against **95,0 % of a Cantal block and 98,6 % of a Landes forest one**. The layer reports that fraction so the gaps read as the public realm rather than as a broken feed.
- **`contenance` is the DGFiP's registered surface, not a measurement of the polygon, and both are shown.** Mamoudzou publishes parcels with `contenance: null` (74 in one box) and Ostwald one at exactly `0` — and `Number(null)` is `0` in JavaScript, which would turn "not published" into "declares zero square metres". Where both figures exist they disagree: of 9 539 parcels with a usable contenance, **7,2 % differ by more than 5 % and 1,0 % by more than 20 %**, headed by a Toulouse parcel whose plan encloses 494 m² against 153 m² declared. Neither number is a survey, so the card prints both and never averages them.
- **Courtyards are holes, parcels can be in two pieces, and sections are not always letters.** 0,5 % of parcels carry an interior ring — the Palais-Royal's `75101000AJ0002` among them, where dropping the courtyard moves the area from inside 1 % of the declared contenance to outside 5 % — and a handful are multi-part: one identifier, two disjoint polygons. Alsace-Moselle numbers its sections (`22` in Ostwald), Marseille prefixes with a digit (`0D`), and `com_abs` — the API's name for the IDU's three-digit préfixe — runs 801–842 across Toulouse, a commune with no arrondissements at all. All are carried as opaque strings and none is parsed for meaning.
- **`source_ign=BDP` is a different dataset and is not used.** The parameter switches Api Carto from the live PCI to IGN's older BD Parcellaire, whose features carry neither `idu` nor `contenance` and whose geometry differs. The default (PCI) is the one the DGFiP maintains, and it is the only one this layer reads.
- **Paris road counts (comptages routiers permanents).** Keyless, ODbL, `access-control-allow-origin: *`. The dataset is **27,772,889 rows** and the fold is done once on the server, because the answer is a 24-hour profile per arc and re-deriving it in every open tab would be absurd. **The feed is not live: it is J-2.** Measured 2026-09-01T21:02Z, `metas.default.data_processed` = 2026-09-01T01:02:50Z, `dcat.accrualperiodicity` = *Quotidienne*, `dcat.granularity` = *Horaire*, and `max(t_1h)` = 2026-08-30T22:00:00Z — a nightly batch landing ~46 h behind the wall clock. The word "live" appears on no surface of this layer; the edition is the last COMPLETE local Monday–Sunday week, discovered from `max(t_1h)` and floored at `COMPTAGES_WEEK_FLOOR` (2026-08-24), because a discovery older than the floor is a malformed answer rather than a new fact.
- **A third of the counting network measures nothing, and it is drawn as silence, not as calm.** Built live against the week of 2026-08-24 → 08-30: of **2,977 arcs**, 1,730 count vehicles, 356 publish occupancy but no count, and **891 publish neither, in all 168 hours**. The publisher's own `etat_barre` explains 891 of them as 724 *Invalide*, 141 *Ouvert* and 26 *Barré* — so 141 arcs are declared open and still report nothing. A silent arc receives `bin: null` and a colour that is deliberately **not a member of the flow ramp**, asserted in `comptagesRhythm.test.mjs` and again in `comptagesParis.test.mjs`; giving it the ramp's quietest step would claim a measurement on 891 real streets. `comptagesFlowBandLabel()` guards on `typeof bin !== 'number'` rather than coercing, because `Number(null)`, `Number('')` and `Number([])` are all `0` and a coercing guard prints "< 100 véh/h" for an arc that counted nothing.
- **The geometry does NOT come from the referential, and that is a measurement, not a preference.** The obvious source is `referentiel-comptages-routiers`, and it is wrong: measured 2026-09-01, **3,739 rows for only 3,348 distinct `iu_ac`** — 338 ids repeated with no usable tiebreak, since `date_fin` maxes at 2023-01-01 on 3,303 of them while those same arcs are demonstrably still counting in 2026. It also misses 31 arcs that ARE counting and carries 402 that are not. The counts export carries its own `geo_shape` on every row: **2,977 features for 2,977 distinct ids**, one row per arc, fresher, and 0.27 s against 7.7 s. The referential is not fetched at all.
- **31 arcs count from nowhere, and nothing places them.** 31 of the 2,977 features publish `"geometry": null` — the same 31 whose `date_debut` and `date_fin` are also null, rows the referential never received. **19 of them are actively measuring.** They are counted on the national card and named in the loading line ("19 arcs mesurés sans géométrie publiée") rather than dropped or pinned to a street they might not be on.
- **Ten upstream calls, and the clock is split because the server says so.** One `max(t_1h)` for the edition, one GeoJSON export pinned to the week's closing hour for geometry and names, eight grouped aggregations, and one `etat_barre` roll-up. The grouped endpoint caps `offset + limit` at 30,000 and one day-type is 2,977 arcs × 24 h = 71,448 cells, so the clock is fetched six hours at a time (17,862 cells — inside the ceiling with room for the network to grow by two thirds). Losing the `etat_barre` roll-up is **not** fatal: it costs the reason a silent arc is silent and the layer degrades to "silent, reason unpublished". Cold build measured end to end against the live portal: **3.1 s**, 1,374,165 bytes raw and **305,250 bytes gzipped on the wire**.
- **Two ODSQL traps, both of which return a 400 rather than a wrong answer.** An alias may not be declared in both `select` and `group_by` — `hour(t_1h) as h` in both yields *"Alias 'h' is declared several times"* — so `COMPTAGES_PROFILE_SELECT` deliberately omits `h`. And `group_by=iu_ac` returns a junk group whose id is the literal `*`; it is filtered by `COMPTAGES_PHANTOM_ARC` and counted, and the live build reports **0 phantom, 0 duplicates**.
- **`etat_barre` is documented as integers and published as French words.** The field description states `0=inconnu; 1=ouvert; 2=barré; 3=Invalide`; the API returns *Ouvert*, *Barré* and *Invalide*, and `0`/`inconnu` never appears. Measured over the week: Ouvert 357,679 · Invalide 128,729 · Barré 13,728 = 500,136. Coding against the documented integers finds nothing at all.
- **Recorded crime (SSMSI), and the secrecy rule is the layer.** Keyless, Licence Ouverte 2.0, edition 2026-07-09. Two bases are read: `DEP` (2,001,231 bytes of CSV) and `COM` (39,932,450 bytes gzipped, **5,238,000 rows**, streamed through the fold one line at a time because it inflates to roughly a gigabyte of text and is never buffered whole). Measured on the live build: 101 départements, **34,920 communes**, 15 commune indicators, years 2016–2025, folded to the newest year present (2025), in **8.8 s**. The `slowLines` counter — non-zero would mean the fast `split(';')` path was wrong for some line and the quote-aware walk took over — reads **0 across all 5,238,000 rows**.
- **Suppression does not exist at département grain and dominates at commune grain.** This is the single most important fact about the dataset and it is measured, not assumed: the DEP base has **no `est_diffuse` column at all**, and its 18,180 cells are 17,711 published + 469 measured zeros + **0 suppressed**. The COM base is the opposite. Share of the 34,920 communes whose cell is withheld, 2025: escroqueries **69.8%**, cambriolages **69.4%**, dégradations **67.9%**, vols sans violence **67.3%**, violences intrafamiliales **65.2%**, violences sexuelles 59.3%, vols de véhicules 54.4%, violences hors famille 51.4%, vols dans les véhicules 48.6%, vols d'accessoires 47.5%, usage de stupéfiants 44.4%, AFD stupéfiants 29.3%, trafic de stupéfiants 20.5%, vols violents 14.9%, vols avec armes **9.0%**. In the Creuse, **252 of 255 communes** carry at least one withheld cell. A choropleth that renders those as zero, or as the bottom of a ramp, is not a map with a caveat — it is a false statement about twenty-four thousand real places, so a withheld cell has its own colour, is excluded from every quantile, and is never averaged or interpolated across.
- **A withheld cell carries no number, structurally.** On the wire a published cell is `[state, count, rate]` and a withheld one is `[state]` — there is nothing to accidentally read. The departmental mean the publisher attaches to suppressed rows (`complement_info_*`) is hoisted OUT of the cells and served per département, because it is a departmental constant and a card that printed it inside a commune's row would be publishing a number about a place that never published one. Measured on the 2025 slice: 1,470 of the 1,472 (département, indicateur) pairs carry exactly one distinct `complement_info_taux`; the two that do not are (13, Vols avec armes) and (69, Vols avec armes), because Marseille's 16 and Lyon's 9 arrondissements form their own suppressed sub-population with their own mean. The modal value is kept and the variant count reported, so a card can say the mean is not unique here rather than quietly picking one.
- **The quantile ramp is cut nationally, once.** Thresholds are computed over every published commune rate in France and handed unchanged to every département pack. Re-cutting per pack would rebin a quiet département against its own quiet neighbours and paint it like a busy one — the same colour would stop meaning the same rate the moment the camera moved.
- **The two sides disagree by design, and the payload says how.** Commune contours come from geo.api.gouv.fr per département. Measured: every contour has an SSMSI row, and 45 SSMSI codes have no contour — the 20 arrondissements of Paris, 16 of Marseille, 9 of Lyon, whose parent communes are drawn and carry the same totals. They are reported as `unshaped` (a finer grain folded away, never a loss) rather than dropped silently. Live check: Paris returns 1 drawn commune and 20 unshaped, Bouches-du-Rhône 119 and 16, Creuse 255 and 0.
- **It is RECORDED crime.** The bases count what police and gendarmerie registered. That is a function of reporting rates and of force presence as much as of offending, and rates are per-population with all the denominator problems that implies. The layer states this in its header, on every card and in its legend, because a choropleth of this data without that sentence is a defamation machine pointed at whole communes.
- **A planned site is not a transmitting site, and it is 8.05% of the file.** Measured 2026-09-02 from the portal's own `refine.statut` counts, not sampled: `En service` **639,019**, `Techniquement opérationnel` **120,891**, `Projet approuvé` **66,508** of 826,418. Folded to supports, **3,638 (5.00%) radiate nothing at all** and a further 15,606 radiate today while carrying an approved project — of which only **3,776** would add a generation the mast does not already have; the other 11,830 are operators re-filing for a band that is already on the air. The layer's colour channel reads the RADIATING mask and never the approved one, a support with nothing radiating is drawn as a hollow ring, and the 3,776 real upgrades get the same pale ring on a filled dot. The register agrees with itself: `emr_dt` is null on **66,321 rows and every single one is `Projet approuvé`**.
- **"Techniquement opérationnel" is a fact about 5G, not about a mast.** Cross-tabulated over all 826,418 rows on 2026-09-02: every one of the 120,891 technically-operational rows is 5G, and **not one 5G row in this edition is ever `En service`**; the 639,019 `En service` rows are all 2G, 3G or 4G. So the status field is how ANFR files 5G nationally, not a signal about one operator's rollout at one address — the standard journalistic mistake with this dataset is to count "technically operational" as not-yet-coverage. The card reports which generations are in which status per support; the panel chip explains once why they always come out the same way.
- **The pre-joined mobile mirror is shipped, not the 380 MB bulk register — because ANFR has already done the hard exclusion.** The canonical file (data.gouv.fr `551d4ff3c751df55da0cd89f`, 453,875 bytes of metadata, 276 resources, licence `lov2`, monthly, last_update 2026-08-24T08:19:37+00:00) is a 66,019,086-byte zip of five semicolon tables, and getting a generation out of it means joining SUP_SUPPORT → SUP_ANTENNE → SUP_EMETTEUR on the COMPOSITE key `(STA_NM_ANFR, AER_ID)` and then classifying 68 distinct `EMR_LB_SYSTEME` strings by prefix — which sweeps in `GSM R` (the railway network), `LTE 700 P` / `LTE 2600 P` (the Réseau Radio du Futur) and four `Expe` labels, several thousand masts that are not consumer infrastructure. The observatoire has already excluded all of them: measured over the whole file it carries **exactly 13 distinct `emr_lb_systeme` values**, all of the form GSM/UMTS/LTE/5G NR + a band, with no `R`, no `P` suffix and no `Expe`. The bulk register is still used, for one 785-byte member of its 4,805-byte reference archive: `SUP_NATURE.txt`, 38 rows, the only place `nat_id` is spelled out. Its own placeholders — `0;Sans nature`, `51;XXX`, `999999999;Support non décrit` — pass through unchanged.
- **The CSV is not the CRLF file next door, and it opens with a BOM.** The 5 W bulk tables are CRLF; this 181,988,412-byte CSV is **LF only** — verified byte by byte, zero `\r`. A parser written for the sibling leaves a trailing carriage return on the last column, which is `statut`, so every `=== 'En service'` test fails and the whole map turns into approved projects. It also opens with a UTF-8 BOM, so `header.split(';')[0]` is `"\uFEFFid"` and a column-index build silently loses `id`. What it is NOT is quoting-hostile: all 826,418 rows split into exactly 22 fields on `;` and the only quoted column is `coordonnees`.

TomTom data is served live and cached only transiently (≤120 s TTL under `.gev-cache/`, gitignored) — it is not bundled or redistributed. One 23 KB point-in-time tile snapshot is committed as a decode-test fixture (`src/data/fixtures/`, © TomTom, never served to the app).
- **Re:Earth Terrain.** Keyless (no API key). Used two ways: (1) `src/mapStackController.js` swaps in a `Cesium.CesiumTerrainProvider` pointed at Re:Earth's `cesium-mesh/ellipsoid` quantized-mesh endpoint for globe stacks without a Cesium ion token (e.g. OSM), replacing a flat `EllipsoidTerrainProvider`; falls back to the flat provider if the endpoint can't be reached. (2) The server-side `/api/terrain/heights` proxy (disk-cached, serve-stale) resolves per-point ellipsoidal ground height for entity placement. Both are best-effort with a keyless-safe fallback (bundled EGM96 geoid math) if Re:Earth is unreachable.
- **Global Context installation context.** `/api/military-installations` queries only an allow-listed subset of OSM `military=*` and `landuse=military` features inside a maximum 10° non-dateline viewport. It caches and may serve stale mapped context, but it is neither a global installation database nor evidence of capability, activity, or absence. User-requested Google Places results remain separately sourced candidates unless their returned types explicitly establish military classification; generic offices, museums, and similarly ambiguous matches are excluded from military proximity counts.
- **Cockpit regional briefing.** `/api/regional-brief` rounds aircraft coordinates into 0.1° cache cells, caches results for five minutes, and serializes Nominatim calls at no more than one request per second. Google News RSS is queried with the resolved locality/region first; GDELT is used only when that RSS query fails or is empty. Google's published Google News terms restrict that source to personal, noncommercial use, so commercial deployments must disable/replace it or obtain separate permission; GDELT permits commercial dataset use with citation. The Data attribution popover identifies the active headline sources; article links retain publisher attribution. Headlines are location-query matches, not verified incidents, risk rankings, or evidence that a location is safe. Empty, partial, stale, and unavailable source states remain distinct. Open-Meteo supplies current conditions independently of the news source. `WX OFF` disables cockpit weather rendering only; the Local Info briefing still fetches its source-backed weather values and displays the required linked Open-Meteo credit.
- **Dynamic weather presentation.** While cockpit mode is active, `/api/weather-effects` requests current Open-Meteo observations for the aircraft/camera location, rounds coordinates into 0.1° cache cells, caches results for five minutes, and may retain a stale observation for up to 30 minutes during a transient outage. WMO condition code selects the visual family; observed cloud cover, precipitation, visibility, wind speed, and wind direction bound its strength and motion. Missing or expired weather renders no synthetic atmospheric effect, and normal globe view never renders the weather overlay.

### OurAirports (`airports/`)

`airports/airports.geojsonl` bundles a **selection** of the OurAirports
catalogue — 7,464 of its 86,002 rows — with ICAO/IATA codes, municipality,
country, elevation and a runway summary (longest open runway in metres, surface
family, lit, record count). Retrieved 2026-08-31 from
`https://davidmegginson.github.io/ourairports-data/` (the daily mirror of
`ourairports.com/data/`) and transformed by `scripts/build-ourairports.mjs`.

OurAirports **dedicates its data to the public domain** — *"You may use it for
any purpose, including commercial."* No permission needed, no attribution
legally required. We credit OurAirports and its volunteer editors anyway.

Three things about this pack are easy to get wrong, and all three are documented
in `airports/README.md` and enforced by `src/data/airportsPack.js`:

- **It is a selection, and the selection is asymmetric.** Worldwide it carries
  every large/medium airport and everything that sells a scheduled seat; inside
  France and the overseas territories it also carries the whole long tail down
  to the grass strips (1,335 features). A small airfield missing outside France
  was **not selected** — it is not evidence of an empty sky.
- **`type` is OurAirports' editorial SIZE bucket, not a legal category.** It does
  not map onto the French ladder (aérodrome d'intérêt national / régional /
  local). The rendered *Grand aéroport* / *Aéroport* / *Aérodrome* translate the
  bucket; they do not grant a status.
- **`runways.count` counts upstream runway RECORDS, helicopter lanes included.**
  Charles de Gaulle reports 5, of which four are its paved runways.
  `runways.surface` is likewise a three-value family collapsed from 557 free-text
  spellings, and is omitted rather than guessed when unreadable.

Positions and elevations are volunteer-maintained. **Not usable for navigation.**

The layer grades every feature into four importance tiers (`large_airport` first, then
scheduled service, then the `medium_airport` remainder, then everything else). The tier
drives the dot size, the colour, the label ladder and how far out the card stays
readable, and four row chips filter by it. Those chips are runtime params, not
share-link state: the pack always ships whole and the layer keeps reporting all 7,464
features, so a floor hides markers without losing them.

### NGA World Port Index (`ports/`)

`ports/ports.geojsonl` bundles the U.S. National Geospatial-Intelligence Agency's
**World Port Index** (NGA Pub. 150) — 2,951 ports with country, region, UN/LOCODE,
harbour size/type, shelter rating, approximate depths and water body. Retrieved
2026-08-26 from `https://msi.nga.mil/api/publications/world-port-index?output=json`
and transformed by `scripts/build-nga-ports.mjs` (deterministic; provenance and the
full field-by-field rationale live in `ports/README.md`).

As a U.S. Government work it is **public domain** — no permission needed, no
attribution legally required. We credit NGA anyway.

Two properties of this dataset are easy to get wrong, and both are documented in
the build script and enforced in the pack:

- **Depths are binned range codes, not surveyed soundings.** They ship under
  `approxDepthM` and render as `~11 m channel (approx.)`. Rotterdam reports an
  11 m channel where the real Maasgeul is dredged to roughly 24 m. **Not usable
  for navigation.**
- **Harbour-size code `V` means *very small*, not "very large"** — the ladder is
  V → S → M → L, verified against Rotterdam/Shanghai/Antwerpen/Busan/Hamburg
  (`L`) and Marseille (`S`).

Fields that are `U` ("unknown") for ~99% of rows — port security, VTS, TSS — and
the max-vessel dimensions (present for 3% of rows, with physically impossible
values) are **dropped rather than shipped**, so the layer never renders a guess
as a measurement.

### Natural Earth physical regions (`natural_earth/`)

Curated from the **Natural Earth 10m physical vectors** (https://www.naturalearthdata.com/ —
fetched from the canonical `nvkelso/natural-earth-vector` GitHub repo, commit
`ca96624a56bd078437bca8184e78163e5039ad19`, 2026-07-28): `ne_10m_geography_regions_polys`
(mountain ranges, deserts, plateaus, peninsulas, islands, …) → `regions.json` and
`ne_10m_geography_marine_polys` (seas, gulfs, straits, bays) → `marine.json`. They back the
voice-annotation resolver's named-natural-region lookup (`src/data/naturalEarthRegions.js`),
so "outline the Alps" draws the real range polygon offline.

Curation (provenance in each file's `meta` header): named features only, outer rings only,
Douglas-Peucker simplified at ~0.01° with coordinates rounded to 3 decimals, sub-20 km²
MultiPolygon crumbs and zero-area sliver artifacts dropped (7.3 MB source → 2.5 MB pack).

Natural Earth is **public domain** (no permission needed, no attribution legally required —
https://www.naturalearthdata.com/about/terms-of-use/). We credit anyway: "Made with Natural
Earth". Registration in the in-app `dataCredits.js` attribution list ships with the resolver
wiring (see below).

The required Google Maps / Cesium credit renders on the on-globe credit line (`#cesium-credits`, bottom-left) and must stay visible — including in clean-view and recording modes (the whole line, logo + "Google Maps" + the "Data attribution" link, stays on screen; only the GEV panels/HUD fade).
